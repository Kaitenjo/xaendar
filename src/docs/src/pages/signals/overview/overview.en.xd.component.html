Signals

A signal is a wrapper around a value that notifies its consumers when the value changes. Everything reactive in Xaendar — template bindings, computed signals, effects, queries, component inputs — is built on signals.

Creating and reading a signal

signal(initialValue, options?), exported by {'@xaendar/core/signals'}, creates a writable signal. The signal is a function: call it to read the value. Inside a computed signal, an effect or a template binding, the read also registers a dependency.

Writing

  • set(value) replaces the value.
  • update(fn) passes the current value to fn and sets what it returns. The current value is read without tracking, so calling update inside an effect does not make the effect depend on the signal it updates.

A write notifies the consumers synchronously that something changed; the work they do in response — effects and template bindings re-running — is batched and happens in a microtask. See Effects.

Equality

Before notifying anybody, a signal compares the new value with the current one. By default it uses Object.is: for objects and arrays that means identity, not content.

push changes the array, but the signal still holds the same reference: nothing re-renders, and the pear stays invisible until a new array is set. Setting the same reference again is ignored too. Treat signal values as immutable and always produce new arrays and objects.

Custom equality

The equals option replaces Object.is. Return true when the new value should be considered the same as the current one: the write is then ignored and the old value is kept.

Types

Signal and Computed are the types of what signal() and computed() return. Annotate component members with them when a signal comes from somewhere else, for example from a shared module: see Sharing state.

Edge cases

Mutating the value of a signal — push, splice, assigning a property — notifies nobody, and leaves the template showing stale data. The next real change then reveals every hidden mutation at once. set and update do nothing when the new value equals the current one. With a custom equals the old value is kept: in the example above, typing “ADA” leaves “Ada” in the signal. equals is called synchronously by every set and update, with the current and the new value and with this bound to the underlying Signal.State. Keep it a pure, cheap comparison of its two arguments: if it throws, the write throws. Reading a signal in an event handler or in a plain method just returns the value: nothing subscribes. Only reads made while a computed signal, an effect or a template binding runs are tracked. The type says Signal.State, but signal() returns a function wrapping one: instanceof Signal.State is false and the Signal.subtle API rejects it. See Advanced: Signal.subtle.
