Reading without tracking

untracked(fn) runs fn and returns its result, without recording the signals it reads as dependencies of the computation in progress.

When to use it

Use it when an effect or a computed signal needs the current value of a signal, but should not run again when that signal changes. The classic case is context: here the effect sends every new message, signed by the user logged in at that moment — but switching user must not send anything.

update() is already untracked

sig.update(fn) reads the current value of sig with untracked. That is why an effect can append to a log with update without depending on the log, as several examples on these pages do.

Edge cases

Reads made before or after the call are tracked as usual. And it is the reads that are untracked, not the signals: the same signal read elsewhere in the same effect is still a dependency.

When a computed signal is evaluated inside untracked, the signals read after it, in the same untracked call, are tracked again by the outer computation: note becomes a dependency of the first effect. The polyfill restores the outer computation when the nested one ends, instead of restoring the untracked state.

Workaround: use one untracked call per read — {'untracked(() => total()); untracked(() => note());'} — or read the computed signal outside of it. The same bug makes templates and lifecycle hooks occasionally track signals they read while rendering; see Known issues.
