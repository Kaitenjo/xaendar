Sharing state

Xaendar has no dependency injection. State shared by several components lives in a plain ES module: modules are evaluated once per page, so every component importing one sees the same signals.

A store is a module

Export signals, computed signals and the functions that change them. The two components below know nothing about each other: they only import the same store.

Exposing shared signals to a template

Templates only see the members of their component, so the component exposes the shared signal as a field. How you declare that field matters: the compiler decides whether an attribute binding is reactive by looking at the declaration of the members it reads, not at their values.

Raise the level: the three texts follow it, but the first progress bar stays where it was. Text interpolations are always reactive; an attribute binding is reactive only if it names a member the compiler recognizes as a signal — one initialized by calling a function of {'@xaendar/core/signals'}, or annotated with one of its types.

Edge cases

A member like readonly level = level is evaluated once in attributes. Annotate it with Signal or Computed, or wrap it in computed(). The site you are reading does this for its router and its translations. The detection is syntactic: it only recognizes the names imported from {'@xaendar/core/signals'} in the same file. A type alias of your own, even if it is the same type, is not recognized. A member initialized by calling any other function is not recognized either, whatever its annotation. Module state is shared by every instance of every component, and survives them: removing all the components does not reset the store. Reset it explicitly when needed, for example between tests.
