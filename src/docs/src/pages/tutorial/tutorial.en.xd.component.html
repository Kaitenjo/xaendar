Tutorial: a todo app

Build a small todo application in five steps. Each step adds one concept, and each example is the complete, working code of that step: compare the files of two consecutive steps to see exactly what changed.

Step 1 — A static component

Every component starts as a class decorated with {'@WebComponent'}, pointing at its template and its stylesheet. The template is plain HTML for now.

Step 2 — State in a signal

The todos move into a signal. The template renders them with {'@for'}, and shows their number with an interpolation. track todo.id tells {'@for'} how to recognise a todo across changes, so that its DOM can be reused.

Step 3 — Adding todos

The (submit) listener calls add($event), which reads the form, appends a todo and resets the form. The update produces a new array: signals compare values by identity, so pushing into the existing array would notify nobody.

Step 4 — Completing and removing

Each row gets a checkbox and a remove button. A conditional binding, {'@if (todo.done) { checked }'} written inside the tag, adds the checked attribute only to the done todos. A computed signal counts the remaining todos, and {'@if'} shows a message when the list is empty.

Toggling a todo replaces it with a new object that has the same id. {'@for'} reuses the row of a key it already knows, and the row keeps showing the object it was created with: tracked by todo.id, a toggled todo would not be redrawn. Tracking by the object itself renders a new row for the new object. See Lists with {'@for'}.

Step 5 — A child component and a filter

The row moves into its own component, ex-todo-item. It receives the todo through a required input and reports what happens through two outputs, doneChange and removed. The parent keeps the state and adds a filter: a signal, a computed list of the visible todos, and a {'@switch'} for the footer.

A child component is rendered as soon as it is inserted in the page, and the parent binds its inputs right after. During that first render todo() is still undefined, even though the input is required: reading todo().title would throw, and stop the rest of the child template from rendering. Optional chaining keeps the first render safe; the bindings update as soon as the input is set. See Inputs with {'@Property'}. The input of ex-todo-item is typed with an inline object type instead of the Todo type alias. The compiler copies the type of each input, as text, into the code that type-checks the templates binding it, where an imported alias would not be found. See Known issues.
