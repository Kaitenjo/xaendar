Directives

A directive adds behavior to an element that a template renders, without wrapping it in a component. Xaendar has two kinds: custom directives, written {'@@name'}, act on an element that exists; and structural directives, written *name, decide whether the element exists at all.

Two kinds of directives

exTint extends CustomDirective: it receives the element it is applied to in this.element, and an effect keeps its background in sync with the color input. exVisibleWhen extends StructuralDirective: it has no element, only a shouldRender() method, and the paragraph exists while the method returns true. Both declare their inputs with {'@Property'}, exactly like components.

Syntax

The inputs and the listeners of a directive go between the parentheses after its name, with the same syntax as the attributes and the listeners of a tag. Without inputs, the parentheses can be left out. An element can have several directives of both kinds.

Custom directives are covered in Custom directives, structural ones in Structural directives, and directives applied by an {'@if'} inside a tag in Conditional directives.

Declaring and registering

{'@Directive'} takes a selector and registers the class under it as soon as the module is evaluated. As for components, a directive has to be known twice: the template imports it with {'@import'}, so that the compiler can check its inputs and outputs, and the module has to be loaded at runtime before a template using it is rendered. A glob in main.ts takes care of the second part for every directive of the application.

Selectors of directives live in a single registry, shared by the whole application and by the libraries it uses. Unlike the names of custom elements, they need no dash: a short prefix, such as ex in these pages, avoids clashes.

Edge cases

The compiler only knows the directives imported by the template, and rejects the others, even when they are registered at runtime.

The opposite case compiles: the template imports the class, but no code loads its module before the template is rendered. The decorator never runs: the element using the directive stays empty, and nothing after it in the template is rendered.

The registry accepts a selector once. The compiler reports the clash as soon as it has met both directives, while compiling the templates importing them; at runtime, the second decorator throws when its module is evaluated, even if no template uses it.

The compiler does not check that {'@@'} is used for custom directives and * for structural ones. The mistake shows up when the element is rendered.
