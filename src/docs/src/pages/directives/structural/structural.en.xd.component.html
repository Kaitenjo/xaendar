Structural directives

A structural directive extends StructuralDirective and implements one method, shouldRender(). The element it is applied to, with everything inside it, exists while the method returns true. It is an {'@if'} with a name, inputs and logic of its own, reusable in any template.

shouldRender

shouldRender runs inside an effect: it is evaluated again whenever a signal it reads changes, here the value input. When the outcome becomes true the element is rendered; when it becomes false the element and its subtree are destroyed.

The second paragraph has two structural directives: it is rendered only while all of them return true. The order does not matter, and there is no limit on their number.

Type something in the field, then press +2: the outcome stays true, so the element is left alone and keeps the text. Press +1 and then +1 again: the element is destroyed and created anew, with an empty field. The same happens with {'@if'}, as shown in {'@if'}.

Inputs

A structural directive can have any number of inputs, declared with {'@Property'}. Since min is a number, it is bound with an expression, {'min="{ 3 }"'}: a static value would be a string, and the compiler would reject it.

Reading other signals

shouldRender tracks every signal it reads, not only the inputs. A signal kept in a module can make the rendering follow the state of the browser.

The signals are created once per media query and shared by all the instances of the directive. A structural directive has no onInit or onDestroy, so it has nowhere to remove a listener it adds: any resource it needs has to live outside of it, like the map of this module.

Asynchronous directives

shouldRender can return a promise. The element is rendered or destroyed when the promise settles: until then, it stays as it is.

Switch to Guest: the panel stays visible during the check, and disappears when the answer arrives. Then try the third button: the check for the guest is still running when the one for the admin starts. When the first answer arrives, the directive has already been evaluated again, so the outcome is discarded: only the latest evaluation decides, and the panel never flickers.

Edge cases

Only the signals read before the first await are tracked: after it, the evaluation is no longer running inside the effect. The second directive reads its input after waiting, so switching user does not evaluate it again, and the paragraph stays. Read every input at the top of the method, as the first directive does.

An asynchronous directive starts with no outcome: the element is not rendered until the first promise resolves to true. A promise that rejects leaves the previous outcome in place, and its error reaches the console as an unhandled rejection: catch it in the method if a failure should hide the element.

A structural directive has no element to dispatch events on, since the element may not exist, so it accepts no listeners. Its inputs cannot be bound conditionally either; the directive itself can be applied by a condition, as shown in Conditional directives.

An attribute without a value, such as hidden, written right before a structural directive is not parsed. Moving it after the directive, or giving it an empty value, works around the problem.
