CLI

xd, from {'@xaendar/cli'}, creates projects and components, and runs Vite with the plugins Xaendar needs. There is nothing more to it: vite.config.ts stays a plain Vite configuration.

xd new

The name of the project is used for the folder, for package.json, and for the root component, {'-root'}. The generated files are described in Installation. The command stops if the folder exists and is not empty.

xaendar.json records the settings of the project. Today it holds only the extension chosen with --style.

xd start and xd build

xd start (or xd s) runs the Vite dev server, xd build (or xd b) a production build. Both read vite.config.ts from the current folder and add two plugins to it: Babel, to compile the decorators, and the Xaendar plugin, to compile templates and styles. The details are in Build and Vite plugin. Everything else, such as the port, the root folder or the output folder, comes from the Vite configuration.

xd component

The command creates a folder named after the component, with the class, the template, the stylesheet and a spec. The name is used as the selector, so it must be a valid custom element name; the class is named after it in PascalCase.

Remember to import the new component: in main.ts, or through a glob, so that it is defined, and in the templates using it, with {'@import'}.

Edge cases

The component command is meant to live in a generate group, with the alias g, but it ends up registered at the top level. Use xd component or xd c.

Component names are checked before anything is written.

The name of a project, instead, is checked only when the root component is generated, after the other files have been written.

xd new accepts scss, less and styl, but the plugin compiles only .css files. xd component, on its side, ignores xaendar.json and always writes a .css file.

The generated package.json runs Vitest, which knows neither the decorators transform nor the Xaendar plugin: the spec of the root component fails before running. Testing components requires a Vitest configuration with the same plugins and a DOM environment.

The packages published on npm as 0.12.0 predate the API described in this site: their {'@xaendar/core'} exports BaseWebComponent instead of CustomElement. A project created by a CLI built from the repository installs them, and its build fails. Until the next release, work inside the repository, as this site does.

A template that does not compile is reported, but the build goes on and succeeds: the component reaches the bundle without a render function. Check the output in automated pipelines.
