Routing

Xaendar has no router, and a small one takes a few dozen lines: a signal holding the path, a computed signal matching it against the routes, and an {'@switch'} rendering the page of the route. This site is built that way.

A router in a module

router.ts holds the state of the whole application: path, the history of the visited paths, and route, a computed signal matching the path against patterns such as /users/:id. Any component importing the module shares that state, with no injection: see Shared state. The members exposing module signals are annotated with their type, so that the attributes reading them are reactive.

The links keep their href, so they still work as links for the browser and for assistive technologies; a click listener calls preventDefault() and navigates instead. The active link gets aria-current through a conditional binding, and the stylesheet uses it.

The parameter of the user page reaches a component as an input. Going from user 1 to user 2 keeps the same component and changes the input; going to another route destroys it, along with its state.

Reading the URL

The router of the example keeps the path in memory, because this site already uses the address bar. A real router reads it from the URL, so that pages can be bookmarked and the back button of the browser works. With the hash, the change is small:

Edge cases

In a template, location and history are the globals of the browser, even when the component has members with those names, as shown in Expressions. Pick other names for the members of a router, such as path and visited. A page component imported lazily must be defined before the template using it is rendered: one rendered earlier receives its inputs as plain attributes. See Selectors and registration. The {'@switch'} destroys the page it leaves. State that has to outlive a page, such as a filter or a draft, belongs in a module, like the router itself.
