Lists and CRUD

A list is a signal holding an array, replaced by every change, and rendered by an {'@for'} with a stable key. Filters, sorting and totals are computed signals over it. Fields that change often can be signals themselves, so that a change updates one cell instead of a row.

An inventory

items is never mutated: adding, inserting and removing all write a new array, as signals compare values with Object.is, explained in Signals. The {'@for'} tracks item.id: when the array changes, the rows of the items still present are kept and moved, and only the new ones are created. Insert an item at random, or sort the list: the existing rows move, untouched.

visible filters and sorts the items in a computed signal, and the template only renders it; the original order stays in items. The ids come from a counter and are never reused, so the keys stay unique even after removals.

The quantity of each item is a signal of its own. The + and − buttons update it in place: the array does not change, no row is touched, and only the cell and the total, a computed signal reading every quantity, are written.

The form is read with FormData and cleared with form.reset(): the field has no bound value, so restoring its initial value empties it, with no directive needed. See Forms for fields driven by the state.

Edge cases

A new object with the same key does not update its row: the row keeps showing the object it was created with. This is why the quantity is a signal.

The details, and the other pitfalls of keys, are in {'@for'}.

Two items with the same key corrupt the list. Derive keys from a counter or from the ids of the server, never from the position or from a field that users can edit, such as the name.

OperationCode
Add{'items.update(list => [...list, item])'}
