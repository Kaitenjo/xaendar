Async data

Signals hold values, not promises. Loading data means writing signals when the answer arrives: one for the state of the request, one for the data, one for the error. The template then renders whatever state it finds.

Loading, error, data

load is an ordinary async method. It sets status to loading, awaits the fake server, and writes either the user or the error. An {'@switch'} over status picks what to show. Writes after an await are fine: only reads after an await escape tracking, and here nothing reads signals.

The request is tied to an AbortController: a new request aborts the one in progress, and so does onDestroy, so that no answer arrives for a component that is gone.

Requests that overtake each other

User 1 is slow and user 2 is fast. The naive loader writes every answer in the order it arrives, so it ends up showing user 1, which was asked for first. The other loader aborts the stale request, and shows user 2. When an API cannot be aborted, the same result comes from a counter: each request remembers its number, and an answer is written only if no newer request was sent.

Loading when an input changes

A component loading data for one of its inputs can start the request from an effect, which runs again whenever the input changes. The request itself runs in untracked, so that whatever it reads does not become a dependency of the effect.

Edge cases

In onInit, the inputs of a component still hold their default values: the effect starts a request for the default, and the bound value, arriving right after, starts another one. Aborting the request in progress makes the first one harmless; alternatively, the effect can skip the default value. Code after an await runs outside of the effect that started it, so the signals it reads are not tracked. Read what the request depends on before the first await. The same rule applies to asynchronous structural directives.
