Forms

Xaendar has no form module and no two-way binding. A form is made of plain elements: their events write signals, computed signals validate them, and a directive writes values back into the fields when the state has to drive them.

Reading the fields

Each field has a listener writing its signal: input for text fields, change for selects and checkboxes. The method receives the event and reads value or checked from its target, since a template cannot read $event.target itself, as explained in Events.

errors is a computed signal over the fields, so it is always up to date, and the template shows it only after the first attempt to submit. The submit listener calls preventDefault(), which keeps the browser from reloading the page; novalidate turns off the validation of the browser, replaced here by the computed one.

Writing the fields

Reading is enough as long as the user is the only one changing the fields. When the state changes them too, with a reset, a default or a formatting, binding value is not enough.

Type in the first field, then press Reset: the signal is cleared, the field is not. A binding sets the value attribute, which a field only uses as its initial value: once the user has typed, the field shows its value property, and ignores the attribute. The second field uses exBindValue, a directive writing the property in an effect, and follows the signal in both directions. The same directive drives the select.

The directive skips the write when the field already holds the value: writing it again while the user types would move the caret to the end.

Edge cases

A custom directive starts before the children of its element are rendered, as shown in Custom directives. A select has no options yet in onInit, so a value written there is lost and the first option stays selected. exBindValue starts its effect a microtask later, when the options exist.

checked is a boolean attribute: bound to false, it still checks the box. And, like value, it is only the initial state.
