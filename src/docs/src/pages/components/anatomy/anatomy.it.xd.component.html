Anatomia di un componente

Un componente Xaendar è un custom element standard: una classe che estende CustomElement, decorata con {'@WebComponent'}, più un template HTML e un foglio di stile facoltativo. Il compilatore trasforma il template in una funzione di render al momento della build; a runtime il browser crea, collega e rimuove l’elemento come qualsiasi altro tag.

Tre file

Il suffisso del file della classe non è una convenzione ma un requisito: il plugin Vite compila solo le classi dichiarate in file che terminano con .xd.component.ts. Template e foglio di stile possono avere qualsiasi nome, perché è il decoratore a indicarli.

Nell’esempio qui sopra c’è tutto ciò che serve a un componente:

  • lo stato nei signal (value, hovered): scriverne uno aggiorna esattamente i nodi che lo leggono;
  • lo stato derivato nei computed (shown, label);
  • i gestori di eventi nei metodi, chiamati dal template con (click)="rate(star)";
  • le costanti nei membri semplici (stars): il template le legge, ma nessuno viene avvisato se cambiano.

Il template legge i membri pubblici della classe per nome, senza this. Viene controllato rispetto alla classe durante la build: un membro scritto male o un argomento sbagliato fanno fallire la build.

Il decoratore

OpzioneObbligatoriaDescrizione
selector sì Il nome del tag del componente. Vedi Selettori e registrazione.
templateUrl sì Il template, relativo al file della classe.
styleUrl no Un file .css relativo al file della classe. Vedi Stili.

A runtime il decoratore fa due cose: salva il selettore nei metadati della classe, dove lo trova {'@Query(Classe)'}, e chiama customElements.define(selettore, Classe). Il resto avviene durante la build, quando il plugin legge le tre opzioni direttamente dal codice sorgente.

La classe base e lo shadow root

CustomElement estende HTMLElement. Il suo costruttore aggancia uno shadow root aperto, in cui viene renderizzato il template: gli stili della pagina non vi entrano, e quelli del componente non ne escono. Il template viene renderizzato ogni volta che l’elemento viene collegato al documento, e lo shadow root viene svuotato ogni volta che viene rimosso. La pagina Ciclo di vita descrive gli hook che stanno nel mezzo.

La classe è un vero HTMLElement: document.createElement('ex-rating') restituisce un’istanza di RatingComponent, e tutte le API del DOM (attributi, eventi, classList, ...) funzionano come su un elemento nativo.

Casi limite

Il plugin legge selector, templateUrl e styleUrl dal codice sorgente, quindi devono essere stringhe letterali. Con una costante, un template literal o un valore calcolato il plugin salta la classe senza segnalare nulla: il decoratore definisce comunque l’elemento, ma collegarlo lancia un’eccezione. Lo stesso succede a un componente dichiarato in un file senza il suffisso .xd.component.ts.

Un templateUrl che punta a un file inesistente produce un avviso, non un errore di build, e la stessa eccezione a runtime.

Un elemento creato con document.createElement ha uno shadow root, ma vuoto: il template viene renderizzato al collegamento e rimosso alla disconnessione. L’ispettore qui sopra mostra i tre stati.

Il template viene controllato come codice esterno alla classe, quindi può leggere solo i membri pubblici. Un membro private o protected fa fallire la build.

La classe eredita ogni membro di HTMLElement, quindi un signal chiamato title, un input chiamato lang o un evento chiamato remove vanno in conflitto, e TypeScript rifiuta la classe. La build controlla i tipi dei template, non delle classi, quindi l’errore compare solo nell’editor o con tsc. Vedi i casi limite di Output per le soluzioni.

Lo shadow root è sempre aperto, e non si può sostituire: la classe base lo ha già agganciato.
