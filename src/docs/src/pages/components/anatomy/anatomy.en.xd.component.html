Anatomy of a component

A Xaendar component is a standard custom element: a class extending CustomElement, decorated with {'@WebComponent'}, plus an HTML template and an optional stylesheet. The compiler turns the template into a render function at build time; at run time the browser creates, connects and removes the element like any other tag.

Three files

The suffix of the class file is not a convention but a requirement: the Vite plugin only compiles the classes declared in files ending with .xd.component.ts. The template and the stylesheet can have any name, since the decorator points to them.

Everything a component needs is in the example above:

  • state in signals (value, hovered): writing one updates exactly the nodes that read it;
  • derived state in computed signals (shown, label);
  • event handlers in methods, called by the template with (click)="rate(star)";
  • constants in plain members (stars): the template reads them, but nothing is notified when they change. See Shared state for the rule.

The template reads the public members of the class by name, without this. It is type-checked against the class at build time: a misspelled member or a wrong argument fails the build.

The decorator

OptionRequiredDescription
selector yes The tag name of the component. See Selectors and registration.
templateUrl yes The template, relative to the class file.
styleUrl no A .css file relative to the class file. See Styling.

The decorator does two things at run time: it stores the selector in the metadata of the class, where {'@Query(Class)'} finds it, and it calls customElements.define(selector, Class). The rest happens at build time, where the plugin reads the three options straight from the source code.

The base class and the shadow root

CustomElement extends HTMLElement. Its constructor attaches an open shadow root, where the template is rendered: the page styles do not reach inside it, and the component styles do not leak out. The template is rendered each time the element is connected to the document, and the shadow root is emptied each time it is removed. The Lifecycle page covers the hooks in between.

The class is a real HTMLElement: document.createElement('ex-rating') returns an instance of RatingComponent, and every DOM API (attributes, events, classList, ...) works on it as on a native element.

Edge cases

The plugin reads selector, templateUrl and styleUrl from the source code, so they must be string literals. With a constant, a template literal or a computed value the plugin skips the class without reporting anything: the decorator still defines the element, but connecting it throws. The same happens to a component declared in a file without the .xd.component.ts suffix.

A templateUrl pointing to a file that does not exist produces a warning, not a build error, and the same exception at run time.

An element created with document.createElement has a shadow root, but an empty one: the template is rendered on connection, and removed on disconnection. The inspector above shows the three states.

The template is type-checked as code outside the class, so it can only read public members. A private or protected member fails the build.

The shadow root is always open, and it cannot be replaced: the base class has already attached it.
