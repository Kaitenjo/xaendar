View queries

A view query finds elements in the template of the component and keeps the result in a signal. It is the way to reach the DOM from the class: to focus a field, to measure an element, or to call a method of a child component. The result follows the template: when an {'@if'} or an {'@for'} adds or removes elements, the query is updated.

Querying the template

{'@Query'} holds the first element matching a CSS selector, or null. {'@Query.all'} holds all of them, in document order. Instead of a selector you can pass the class of a component: the query uses its selector, and the result is typed as an instance of the class, with its public members.

Add reads the value of the field and empties it through the element found by field, and calls increment() on the badge found by its class. The list is rendered by an {'@for'}, and rows follows it: found, a computed signal reading the query, updates by itself.

A query looks into the shadow root of its component, and only there: it finds the elements the template projects into a child component, since they are written in this template, but not the elements inside the shadow root of the child.

When the result is there

The query is filled right after the render, before afterRender, and it is updated by a MutationObserver each time the elements of the template are added or removed. So it is empty in onInit, and it lags a little behind the changes of the template.

The template is updated in a microtask after the signal changes, and the query a microtask after that. Read queries in afterRender, in event handlers, or reactively in a computed signal or an effect: an effect created in onInit runs again when the query is filled.

Queries without decorators

query and queryAll create the same signals as the decorators, from a field. They are exported by {'@xaendar/core'}.

Edge cases

The observer watches elements being added and removed, not their attributes. Selecting a task changes only its class, so the query on .selected keeps its old result until the list itself changes: add a task and it catches up. Use queries to find elements, and keep the state in signals.

The template compiler recognizes a signal member by the function that initializes it, which must come from {'@xaendar/core/signals'}. queryAll comes from {'@xaendar/core'}, so in an attribute rows is read once, at the render, when the query is still empty: the first meter never moves, and a type annotation does not help, since with a call as initializer only the function counts. Read the query through a computed, or use the decorator, whose accessor is recognized by its type. Text interpolations are always reactive. See Shared state.

A query starts observing when the element is connected, so one created later, for example in afterRender, stays null until the element is connected again, and throws at the next disconnection. Create queries in fields, or with the decorators.

When the element is moved, the template is rendered again from scratch, but the query is refreshed only after the render: in onInit it still holds the elements of the previous render, now detached from the document.

A class passed to a query must be decorated with {'@WebComponent'}, which gives it its selector. Otherwise the query throws when the component is created.

API summary

APIDescription
{'@Query(target)'}The first element of the template matching target, or null.
{'@Query.all(target)'}All the matching elements, in document order. Notifies only when the list changes.
query(this, target), queryAll(this, target)The same queries, created in a field.
targetA CSS selector, or the class of a component.
