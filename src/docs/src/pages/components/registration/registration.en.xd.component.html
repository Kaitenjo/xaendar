Selectors and registration

{'@WebComponent'} registers the class in the custom elements registry of the browser, under its selector, as soon as the module declaring it is evaluated. From then on every element with that tag name, already in the page or created later, is an instance of the class.

Choosing a selector

The selector is a custom element name, and the browser is strict about it: it must start with a lowercase letter, contain a hyphen, contain no uppercase letters, and not be one of the few reserved names such as font-face. A prefix shared by the whole application (app-, acme-) keeps the names readable and avoids clashes with third-party elements.

A name can be defined only once, and a class can be defined under one name only: the example above shows both errors. The compiler checks every component of the project, so two classes claiming the same selector fail the build; without that check, the second define would throw at run time.

Using a component in a template

A template uses a component in two separate steps.

  1. At build time, the template imports the class with {'@import'}. The compiler reads the class to learn its selector, its inputs and its outputs, and type-checks the bindings against them. Nothing of this import reaches the browser.
  2. At run time, the module declaring the class must have been evaluated, so that the decorator has defined the element. The usual way is an entry point that imports every component before rendering anything; this site does it with a glob import:

Loading a component on demand

A component imported with a dynamic import() is defined only when its module arrives. The elements with its tag that are already in the page are then upgraded: the browser runs the constructor on them and connects them, but the bindings applied to them in the meantime did not reach any input, because there was no input yet: they were written as plain attributes, which components do not read.

Click count + 1 first, then load the panel. The first panel shows the default values: its static label will never arrive, and its count only arrives with the next change, since a reactive binding writes the input when its value changes. The second panel is rendered by an {'@if'} only after the module has been loaded, so it gets every binding. That is the rule: render a lazy component only once customElements.get() knows it, or once the promise of customElements.whenDefined() is resolved.

Edge cases

A component imported in a template but never evaluated at run time compiles, and renders as an empty, undefined element: no shadow root, no content, no error. The :defined pseudo-class can style it while it waits, as the lazy example does.

Every tag with a hyphen in a template must be a Xaendar component imported with {'@import'}, so elements from other libraries cannot be written in a template. Create them in code instead, as shown in Using DOM APIs.

There is one registry per page and no way to undefine a name. Two applications on the same page, or two versions of the same library, cannot define the same selector: the prefix is the only protection.
