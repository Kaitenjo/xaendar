Inputs with {'@Property'}

An input is how a parent passes data to a child. You declare it with {'@Property'} on an accessor of the child, and it becomes an InputSignal: a signal that the parent writes through its template and the child can only read. Everything that reads it, in the template or in a computed signal, updates when the parent binds a new value.

Declaring an input

The decorator goes on an accessor field typed {'InputSignal'}, which the decorator replaces with the signal; the ! tells TypeScript that the field is initialized for you. The first argument is the default value, used until the parent binds something. The name used in templates is the name of the accessor, unless alias gives another one: an alias is the way to use dashes, as HTML attributes usually do.

The first meter binds all three inputs; the second binds only value, so max stays 100 and show-value stays true. Inside the meter, percent is a computed signal reading two inputs: inputs are signals like any other, so everything built on them is reactive.

The type of the input can be any type, imported ones included: the templates binding it are checked against it. TypeScript infers the type of the decorator from the default value, so a default such as 'ts', [] or null gives a type that does not match the accessor. Pass the type of the signal to the decorator too, instead of widening the accessor and casting the value where you read it.

Static values and expressions

A binding on a component tag sets the input, not an attribute. Its value is either the text written in the template, always a string, or the result of an expression in braces, of any type. The template compiler checks both against the type of the input.

Normalizing and comparing: transform and equals

transform runs on every value the parent binds, before it is stored. equals compares the result with the current value: when it returns true the input keeps its value and notifies nobody. By default the comparison is Object.is, so a new array with the same content counts as a change.

Send the same tags binds a new array, but once normalized it has the same tags as the current one: the count of runs does not move. Send other tags moves it by one. The first run of the effect happens in onInit, before the parent binds anything, and reads the default empty list: the next section explains why.

Required inputs

{'@Property.required()'} declares an input without a default. Every template using the component must bind it, and the check happens at build time: a template that leaves it out fails to compile, and so does a template that binds it only in some branches of a conditional binding.

When the values arrive

The child is rendered as soon as the parent creates it, before the parent binds its inputs. So in onInit, in the first render and in afterRender, every input still has its default, and a required input is undefined. The bound values arrive right after, and everything that reads the inputs reactively updates.

Add the card and read the log: onInit and afterRender see undefined, the effect runs once with undefined and again with the bound name. Rename re-runs only the effect, and the text of the card. Hence two rules:

  • read inputs reactively: in the template, in computed signals and in effects, never once in a hook;
  • in the template of a component with a required input, handle undefined, as the card does with name() ?? '…': an exception thrown by the first render breaks the template for good. See Known issues.

Edge cases

When the condition of a conditional binding stops holding, the input goes back to its default, 50, not to the last bound value. Binding it again sets the current value of the parent.

An input is not linked to the attribute of the same name: there is no attributeChangedCallback. The button of the second example writes value="42" on the first component, and nothing changes. Code outside Xaendar cannot set an input through the DOM: give the component a method, or wrap it in a Xaendar parent.

InputSignal has no public set: only the bindings of the parent write it. For a value that the component changes too, copy the input into a local signal in an effect, and write the local one.

Templates are checked against the type of the InputSignal, not against the parameter of transform: a transform from string to number does not let you write a static number. Use transforms that keep the type, and bind expressions.

The template compiler only sees the inputs declared in the class of the component, not those inherited from a base class: their bindings compile without any type check. See Inheritance. A component loaded later, for example with a dynamic import, receives its bindings as string attributes until it is defined, and its default values after. See Selectors and registration.

API summary

APIDescription
{'@Property(default?, options?)'}An optional input, holding default until it is bound.
{'@Property.required(options?)'}An input that every template must bind. undefined until it is bound.
aliasThe name of the input in templates.
transform(value)Converts every bound value before it is stored.
equals(a, b)When it returns true, the new value is discarded and nobody is notified. Default: Object.is.
watched, unwatchedCalled when the input gains its first reader and loses its last one. See Signal options.
