What is Xaendar?

Xaendar is a framework for building Web Components declaratively. A component is a TypeScript class plus a template written in an extended HTML5 syntax; the compiler turns the template into code that updates the DOM with the precision of hand-written JavaScript.

Fine-grained reactivity, decided at build time

Most component frameworks run a render function again when the state changes, and compare its output with the previous one: the virtual DOM diff. Xaendar does neither.

At build time the compiler analyses each template and finds, for every element, attribute and text node, the expression that produces it. At runtime each expression becomes a tiny reactive binding, subscribed only to the signals it reads. A signal change runs exactly the bindings that depend on it, and each binding writes exactly one node.

The log comes from a MutationObserver attached to the card. Click the buttons and watch which nodes flash: incrementing touches one text node and one attribute, renaming touches one text node, and the static paragraph never appears.

The building blocks

ConceptWhat it isGuide
Component A class extending CustomElement and decorated with {'@WebComponent'}: a real custom element, rendered in its own shadow root. Components
Template HTML5 extended with interpolation, bindings, events and control flow ({'@if'}, {'@for'}, {'@switch'}), compiled at build time. Templates
Signal A reactive value: whatever reads it, a template binding, a computed signal or an effect, is notified when it changes. Signals
Directive Reusable behavior attached to an element ({'@@name'}), or a condition deciding whether the element exists at all ({'*name'}). Directives
Query A signal holding the elements that match a selector, in the shadow DOM or in the projected content. Queries

The life of a component

  1. Build. The Vite plugin reads every *.xd.component.ts file, finds its template and stylesheet, type-checks the template against the class and compiles it into a render function.
  2. Definition. Importing the class evaluates {'@WebComponent'}, which calls customElements.define().
  3. Connection. When the element enters the document its shadow root adopts the stylesheet, onInit runs, the render function builds the DOM and wires the bindings, and afterRender runs last.
  4. Updates. A signal change re-runs only the bindings reading it, batched in a microtask.
  5. Disconnection. onDestroy runs, then every binding, listener and effect of the component is disposed and its rendered nodes are removed.

What Xaendar does not do

Xaendar is deliberately small. There is no dependency injection, no router, no pipes and no two-way binding: shared state lives in plain modules of signals, formatting lives in methods, and forms are wired with events. The Coming from Angular page maps every Angular concept to its Xaendar counterpart, and the Patterns section shows the idiomatic way to cover the gaps.
