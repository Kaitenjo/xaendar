# @xaendar/core

Runtime primitives for authoring components, plus the runtime of compiled templates (`src/utils/`, see `template-runtime.md`). Depends on `common`, `signals`, `types` and the peer `internals`: **not** on `compiler`.

## Components and directives

- `CustomElement` attaches Shadow DOM and keeps `connectedCallback`/`disconnectedCallback`/`connectedMoveCallback` private (no `attributeChangedCallback`: inputs are not attributes). Its fields are only `declare`d and initialized by `[INITIALIZE]()`, which its constructor calls: never a field initializer, which only its own constructor would run.
- Customized built-in elements (`extends` of `@WebComponent`, `<button is="copy-button">`): `customElementOf(Base)` returns `class extends Base` whose constructor calls `[INITIALIZE]` and whose prototype holds the descriptors of `CustomElement.prototype` (the same functions), one per native class in a `WeakMap` (`HTMLElement` → `CustomElement`): the body of the class is written once, in `CustomElement`. `instanceof CustomElement` holds for them through its static `Symbol.hasInstance` (`INITIALIZE in value`; subclasses keep the ordinary check). A shadow root is attached only for a template (`_getRender`): a template-less one has `_root` `null`, renders nothing and runs `_start` alone. The decorator defines it with `{ extends }` and stores `INTERNAL_EXTENDS`; `getExtendedTagName` gives `createComponent` the tag and `is`, and `@Query` the selector `tag[is="selector"]`. `_createElement(tag, is)` writes the `is` attribute too, so the DOM matches the server's and CSS selectors find it. It and `CustomDirective` have `effect()` and `createComponent()` (options typed `CreateComponentOptionsWithOptionalTarget`: without `target` the component goes into the host element), bound to their lifecycle through `_getComponentRuntime()` (the standalone `createComponent` of `utils/component-creation` goes through it too, with a `null` owner: its component belongs to nothing and lives until `destroy`), which `@xaendar/ssr` swaps with `_setComponentRuntime()` on the server (effects off, components constructed without rendering): never call `effect`/`_createComponent` directly.
- Stage-3 `accessor` decorators, not `experimentalDecorators`. `@Property`, `@Model`, `@Event` and every `@Query` (`lazyQuery`) create an instance's signal, model or `Output` lazily, in the `get` they return, and keep it in the accessor's private storage (`target.get`/`target.set`): never in a decorator variable, which runs once per class and would be shared by every instance. The `init` of `@Property` and `@Model` allocates only for an own property assigned before the upgrade (moved into the input, since it would shadow the accessor). Nothing but a real consumer reads them: the host directives check the exposed inputs and events in the metadata (`INTERNAL_ALIAS_TO_ATTRIBUTE`, `INTERNAL_EVENTS` filled by `registerEvent` for `@Event` and the change events of `@Model`).
- A query signal registers its connection hooks when created, and starts at once when created after the element ran them (`[IS_RENDERED]()`).
- A model (`signals/model`) shares prototypes instead of fields (per-accessor prototype from `createModelPrototype` → `MODEL_PROTOTYPE` → the input prototype), so it costs what an input costs; `set` dispatches `<name>Change` (`toModelChangeEvent` of `@xaendar/internals`, shared with the compiler) only when the value changes, quiet with `INPUT_SIGNAL_SET_SYMBOL`.
- `@HostListener` reads key events with `parseKeyEvent` of `@xaendar/internals`; `_isKey` (`utils/key-event`, also called by the compiled handlers) matches `event.key`/`event.code` in lowercase and the modifiers exactly. `createComponent` types model change events with `ModelChangeListeners`, a mapped type over event names (an `as` clause over `keyof Target` loses the listener types).
- `onLeave(element, handler)` goes through `_ComponentRuntime.onLeave` (`registerLeave` in the browser, no-op on the server), sets `LEAVE_HANDLER` and marks the scope of the starting directive (`startDirective`); see `template-runtime.md`. `CustomDirective.afterRender` goes through `[DIRECTIVE_AFTER_RENDER]` (same `startDirective` wrapping): `CustomElement` calls it on its host directives at the end of `_connect`, after `_bindHost` and before its own `afterRender`; `bindDirectives` calls it right after `DIRECTIVE_CONNECT`, the element having rendered by then.
- The directive registry lets a class with the same name replace the registered one (modules re-evaluated by the dev server).
- Host directives are inherited: `_resolveHostDirectives(klass)` resolves them once per class (a `WeakMap`), the parent's first, reading only the class's own `Symbol.metadata`; `@WebComponent` calls it in its initializer before `customElements.define`, so errors throw at registration. The chain and its host directives are one namespace: a directive once, an exposed input not named like an input, a member (`in prototype`, `HTMLElement` included) or another exposed input, an exposed event not named like an event of the class or another exposed one (the compiler reports the same with `findHostDirectiveErrors`, both through the `describe*` functions of `@xaendar/internals`). A field is an own property the prototype does not hold: `_connect` checks the fields against the exposed inputs with `_checkExposedFields`, once per class (a `WeakSet`), since they exist only after the constructors of the subclasses. Each exposed input gets an accessor on the prototype of the class declaring the exposure, one descriptor per directive class and property (`get` the directive's signal, `set` writes it), for code outside the templates; nothing is defined per element. The exposed events map is shared by every instance. Generated code never goes through that accessor: `_setExposedInput`/`_setExpressionExposedInput`/`_setReactiveExposedInput`/`_resetExposedInput` write into the directive, and before the upgrade keep the value in a `WeakMap` (`PENDING_INPUTS`), never on the element; `_createHostDirectives` takes the own properties (code outside the templates) and then those values.

## Contract with `@xaendar/ssr`

- `@xaendar/ssr` imports `_`-prefixed internals (`_Context`, `_PARENT`/`_COMPONENT`, `_selectBranch`, `_resolveDirective`, `_applyHostAttributes`, `_ComponentRuntime`, `_SSR_MARKERS`, the `_*_ATTRIBUTE` constants, `_RECORDED_EVENTS`, `_EVENT_CONTRACT_KEY`, `_stringifyState`, `_encodeTrackKey`, `_updateInput`, which `renderToString` sets its inputs through so that they are checked as in the templates) and the `Render*` types: the two versions are pinned together (exact peerDependency).
- `CustomElement` assigns `data-xd-inputs` before `onInit`; `getTransferState` reads through `_ComponentRuntime` (page scripts in the browser, request state on the server).
- Hydration: a declarative shadow root is kept (never `attachShadow` on it, never `attachInternals`) and rendered with `claimShadowRoot`. An element inside another component's shadow root waits for that component's `ClaimNodes.mount` to call its `[HYDRATE]`, unless it holds `data-xd-inputs` (interactive child of a static component); both wait for a `data-xd-hydrate` trigger (`utils/hydration-triggers`), recording and then replaying events. `data-xd-client` (`ssr: { render: false }`) has no shadow root and creates its content after waiting.
- `HYDRATION` (`utils/hydration-flag`) guards every path of the hydration in code always bundled (`CustomElement`, `_readPageTransferState`): `typeof __XAENDAR_HYDRATION__ !== 'boolean' || __XAENDAR_HYDRATION__`, which the plugin of `@xaendar/build-tools` defines as whether the project has `ssr`, so that a client-only bundle leaves the hydration out (`true` where nothing defines it: tests, server). Keep it a constant read directly in the conditions (`HYDRATION && …`, `!HYDRATION || …`): read through a function, the bundler no longer folds it. `DEV_MODE` (`utils/dev-mode`) works the same way with `__XAENDAR_DEV__`, falling back on `readDevMode()` (`process.env.NODE_ENV`) where nothing defines it.
- `CustomElement` connects through `runConnection`, so a component's error inside a `@try` is thrown by the template. `_defer` works in any project, with `@hydrate`'s triggers.
- `@xaendar/core/testing` (`src/testing/index.ts`, a `secondaryEntryPoints` sharing core's state) exports `getDeferBlocks`, `setDeferBlockBehavior` and their types; importing it sets `playthrough`, so pages outside tests register no block.
