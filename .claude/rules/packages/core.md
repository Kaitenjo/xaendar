# @xaendar/core

Runtime primitives for authoring components. Depends on `common`, `signals`, `types`: **not** on `compiler`.

- `CustomElement`: attaches Shadow DOM and keeps `connectedCallback`/`disconnectedCallback`/`connectedMoveCallback` private (no `attributeChangedCallback`: inputs are not attributes). It and `CustomDirective` have `effect()` and `createComponent()`, bound to their lifecycle. Both go through `_getComponentRuntime()`, which `@xaendar/ssr` swaps with `_setComponentRuntime()` while it renders on the server (effects off, components constructed without rendering): never call `effect`/`_createComponent` directly from them.
- Decorators `@WebComponent`/`@Directive`/`@Property`/`@Event`/`@Query`/`@HostProperty`/`@HostEvent`, and `InputSignal`. Uses stage-3 (`accessor`) decorators, not `experimentalDecorators`.
- Template-runtime helpers under `src/utils/` (`context`, `for`, `if`, `switch`, `render-*`) called by *compiler-generated* render code, their bindings run by `_bindEffect` (`signals/effect`) and `_runBinding` (`models/effect`): see `template-runtime.md`. The compiler targets this runtime shape without any build-time dependency edge.
- `@xaendar/ssr` imports some `_`-prefixed internals (the `_Context` type and the slots `_PARENT`/`_COMPONENT` of a scope, `_selectBranch`, `_resolveDirective`, `_applyHostProperties`, `_ComponentRuntime`, the markers `_SSR_MARKERS`, the attributes `_SERVER_INPUTS_ATTRIBUTE`/`_TRANSFER_STATE_ATTRIBUTE`/`_HYDRATE_ATTRIBUTE`/`_CLIENT_ATTRIBUTE`/`_SUBMIT_ATTRIBUTE`, the `_RECORDED_EVENTS`, the `_EVENT_CONTRACT_KEY` and `_stringifyState`) and the `Render*` binding types: they are part of the contract between the two packages, whose versions are pinned together (exact peerDependency). Core is the browser side of the rendering on the server: `CustomElement` assigns the inputs of `data-xd-inputs` before `onInit`, and `getTransferState` reads through `_ComponentRuntime` (the page's scripts in the browser, the state of the request on the server). Hydration: `CustomElement` keeps a declarative shadow root (never `attachShadow` on it, never `attachInternals`) and renders it with `claimShadowRoot` (`utils/claim-nodes`); an element inside another component's shadow root waits until that component's `ClaimNodes.mount` calls its `[HYDRATE]`, unless it holds `data-xd-inputs`, written on the interactive components a static one renders, which nothing adopts, and both wait for the trigger of `data-xd-hydrate` (`@WebComponent({ ssr: { hydrate } })`, `utils/hydration-triggers`), recording the events and replaying them once hydrated. A component declaring `ssr: { render: false }` is written with `data-xd-client` and no shadow root: it waits like an adopted element, then creates its content. `_try` and `utils/try-scope` render `@try` (see `template-runtime.md`): `CustomElement` connects through `runConnection`, so that the error of a component a template mounts inside a `@try` is thrown by the template. `_defer` renders `@defer`, in any project, with the triggers of `@hydrate` (`_SSR_MARKERS.defer` around the `@placeholder` the server writes). The secondary entry point `@xaendar/core/testing` (`src/testing/index.ts`, built with `signals` as a `secondaryEntryPoints` of `vite.config.ts`, sharing the state of core) exports `getDeferBlocks` and `setDeferBlockBehavior` of `utils/defer-testing` and their types; importing it sets `playthrough`, so that a page outside the tests registers no block. A mismatch is recovered per block or per element with `console.warn`, without it in a hydration that waited for a trigger, never by rendering the page again. `_encodeTrackKey` encodes the `@for` keys for both sides. The directive registry lets a class with the same name replace the registered one, as a module evaluated again by the dev server defines it.
