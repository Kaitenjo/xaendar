# @xaendar/core

Runtime primitives for authoring components, plus the runtime of compiled templates (`src/utils/`, see `template-runtime.md`). Depends on `common`, `signals`, `types` and the peer `internals`: **not** on `compiler`.

## Components and directives

- `CustomElement` attaches Shadow DOM and keeps `connectedCallback`/`disconnectedCallback`/`connectedMoveCallback` private (no `attributeChangedCallback` of its own: only a class with inputs declaring `attribute` gets one, from `@WebComponent`). Its fields are only `declare`d and initialized by `[INITIALIZE]()`, which its constructor calls: never a field initializer, which only its own constructor would run.
- Shadow root options: `shadowRoot` of `@WebComponent` (`ShadowRootOptions`, `ShadowRootInit` without `mode`) is stored as `INTERNAL_SHADOW_ROOT`; `[INITIALIZE]` attaches `{ ...options, mode: 'open' }` (never `closed`: queries, hydration triggers, the event contract and tests read `element.shadowRoot`). A declarative shadow root is kept as it is: its options are the ones the server wrote.
- Customized built-in elements (`extends` of `@WebComponent`, `<button is="copy-button">`): `customElementOf(Base)` returns `class extends Base` whose constructor calls `[INITIALIZE]` and whose prototype holds the descriptors of `CustomElement.prototype` (the same functions), one per native class in a `WeakMap` (`HTMLElement` → `CustomElement`): the body of the class is written once, in `CustomElement`. `instanceof CustomElement` holds for them through its static `Symbol.hasInstance` (`INITIALIZE in value`; subclasses keep the ordinary check). A shadow root is attached only for a template (`_getRender`): a template-less one has `_root` `null`, renders nothing and runs `_start` alone; one declaring `shadowRoot` without a template throws in the initializer of `@WebComponent` (the compiled static block has registered the render by then). The decorator defines it with `{ extends }` and stores `INTERNAL_EXTENDS`; `getExtendedTagName` gives `createComponent` the tag and `is`, and `@Query` the selector `tag[is="selector"]`. `_createElement(tag, is)` writes the `is` attribute too, so the DOM matches the server's and CSS selectors find it. It and `CustomDirective` have `effect()` and `createComponent()` (options typed `CreateComponentOptionsWithOptionalTarget`: without `target` the component goes into the host element), bound to their lifecycle through `_getComponentRuntime()` (the standalone `createComponent` of `utils/component-creation` goes through it too, with a `null` owner: its component belongs to nothing and lives until `destroy`), which `@xaendar/ssr` swaps with `_setComponentRuntime()` on the server (effects off, components constructed without rendering): never call `effect`/`_createComponent` directly.
- Stage-3 `accessor` decorators, not `experimentalDecorators`. `@Property`, `@Model`, `@Event` and every `@Query` (`lazyQuery`) create an instance's signal, model or `Output` lazily, in the `get` they return, and keep it in the accessor's private storage (`target.get`/`target.set`): never in a decorator variable, which runs once per class and would be shared by every instance. The `init` of `@Property` and `@Model` allocates only for an own property assigned before the upgrade (moved into the input, since it would shadow the accessor). Nothing but a real consumer reads them: the host directives check the exposed inputs and events in the metadata (`INTERNAL_ALIAS_TO_ATTRIBUTE`, `INTERNAL_EVENTS` filled by `registerEvent` for `@Event` and the change events of `@Model`).
- Native form callbacks of host directives: `@WebComponent`, in its initializer before `customElements.define` (when the browser reads them), calls `_applyHostCallbacks(klass, _resolveHostDirectives(klass))` (`utils/host-callbacks`). For each native form callback (`formAssociatedCallback`, `formDisabledCallback`, `formResetCallback`, `formStateRestoreCallback`) a host directive declares, it sets the static `formAssociated` on the class (no option in `@Directive` nor `@WebComponent`: the browser calls those callbacks only on form-associated elements, so declaring one is the declaration) and, when the class chain does not declare it, defines a forwarder on the prototype (module functions of `FORM_CALLBACKS`, shared, never created per class) calling it on every host directive declaring it. Then it throws for a form-associated class with `extends`. `CustomElement` has no member for the forms: `FormAssociatedDirective` of `@xaendar/forms` holds them.
- `@Property(value, { reflect })` reflects an input on the host by declaring the `@HostAttribute` of its accessor (`reflectInput`: `HostAttribute(name)(undefined, context)`), so it follows every rule of the host attributes; the name is the string given, or `toKebabCase` of the alias or the property; `class`/`style` names are rejected, and a structural directive throws at construction (an `addInitializer` added only with `reflect`). Attributes write inputs only through `attribute`.
- `@Property(value, { attribute })` (`utils/attribute-inputs`): `registerAttributeInput` stores `INTERNAL_ATTRIBUTE_INPUTS` (attribute name → `{ property, convert, reflects }`, the map of the parent copied on write), the name by `attributeNameOf` (as `reflect`), the conversion the function given or deduced from `typeof` of the default (`toBooleanInput`: present → `true`; `toNumberInput`; `toStringInput`; module functions, never closures), thrown for a `transform` or another default without function; a directive throws at construction (`INITIALIZE in this`, an `addInitializer` added only with `attribute`). `@WebComponent` calls `_applyAttributeInputs(klass)` before `customElements.define`: `observedAttributes` = the class's own plus the attributes, and `attributeChangedCallback` = the shared `onAttributeChanged`, or a wrapper (one closure per class, only then) calling the class's own after writing the input; a callback the framework gave a parent (`FRAMEWORK_CALLBACKS`) is inherited. The input is written as an assignment from outside (`set`/`reset` with `INPUT_SIGNAL_SET_SYMBOL`), `null` resets it; a reflected input is left alone when the attribute equals `_attributeValue` of its value (the reflection writing it), so no state guards the loop. Static template values of such inputs go through `_setAttributeInput`/`_removeAttributeInput`, writing the attribute itself, or, when it holds the value already (adopted from the server), the input straight away: one conversion, before the upgrade too and on the server, whose `ServerHTMLElement` calls the callback.
- A query signal registers its connection hooks when created, and starts at once when created after the element ran them (`[IS_RENDERED]()`).
- A model (`signals/model`) shares prototypes instead of fields (per-accessor prototype from `createModelPrototype` → `MODEL_PROTOTYPE` → the input prototype), so it costs what an input costs; `set` dispatches `<name>Change` (`toModelChangeEvent` of `@xaendar/internals`, shared with the compiler) only when the value changes, quiet with `INPUT_SIGNAL_SET_SYMBOL`.
- `signal().asReadonly()` (`signals/signal`, on the prototype shared by every signal) returns `this`, typed `ReadonlySignal` (no `set`, no `update`): no wrapper and no run-time check, which would be another signal with a `set` of its own and more memory per signal; the protection is the type-check's. `ReadonlySignal` is one of the `SIGNAL_EXPORTS` the compiler recognizes as a signal member.
- `@HostListener` reads key events with `parseKeyEvent` of `@xaendar/internals`; `_isKey` (`utils/key-event`, also called by the compiled handlers) matches `event.key`/`event.code` in lowercase and the modifiers exactly. `createComponent` types model change events with `ModelChangeListeners`, a mapped type over event names (an `as` clause over `keyof Target` loses the listener types).
- `onLeave(element, handler)` goes through `_ComponentRuntime.onLeave` (`registerLeave` in the browser, no-op on the server), sets `LEAVE_HANDLER` and marks the scope of the starting directive (`startDirective`); see `template-runtime.md`. `CustomDirective.afterRender` goes through `[DIRECTIVE_AFTER_RENDER]` (same `startDirective` wrapping): `CustomElement` calls it on its host directives at the end of `_connect`, after `_bindHost` and before its own `afterRender`; `bindDirectives` calls it right after `DIRECTIVE_CONNECT`, the element having rendered by then.
- The directive registry lets a class with the same name replace the registered one (modules re-evaluated by the dev server).
- Host directives are inherited: `_resolveHostDirectives(klass)` resolves them once per class (a `WeakMap`), the parent's first, reading only the class's own `Symbol.metadata`; `@WebComponent` calls it in its initializer before `customElements.define`, so errors throw at registration. The chain and its host directives are one namespace: a directive once, an exposed input not named like an input, a member (`in prototype`, `HTMLElement` included) or another exposed input, an exposed event not named like an event of the class or another exposed one (the compiler reports the same with `findHostDirectiveErrors`, both through the `describe*` functions of `@xaendar/internals`). A field is an own property the prototype does not hold: `_connect` checks the fields against the exposed inputs with `_checkExposedFields`, once per class (a `WeakSet`), since they exist only after the constructors of the subclasses. Each exposed input gets an accessor on the prototype of the class declaring the exposure, one descriptor per directive class and property (`get` the directive's signal, `set` writes it), for code outside the templates; nothing is defined per element. The exposed events map is shared by every instance. Generated code never goes through that accessor: `_setExposedInput`/`_setExpressionExposedInput`/`_setReactiveExposedInput`/`_resetExposedInput` write into the directive, and before the upgrade keep the value in a `WeakMap` (`PENDING_INPUTS`), never on the element; `_createHostDirectives` takes the own properties (code outside the templates) and then those values.

## Contract with `@xaendar/ssr`

- `@xaendar/ssr` imports `_`-prefixed internals (`_Context`, `_PARENT`/`_COMPONENT`, `_selectBranch`, `_resolveDirective`, `_applyHostAttributes`, `_ComponentRuntime`, `_SSR_MARKERS`, the `_*_ATTRIBUTE` constants, `_RECORDED_EVENTS`, `_EVENT_CONTRACT_KEY`, `_stringifyState`, `_encodeTrackKey`, `_updateInput`, which `renderToString` sets its inputs through so that they are checked as in the templates) and the `Render*` types: the two versions are pinned together (exact peerDependency).
- `CustomElement` sets the inputs of `data-xd-inputs` before `onInit`, only while it hydrates and only into input signals (`isInputSignal`, exposed inputs included): any other name throws, never assigned to the element, since HTML injected with the attribute would write any property (`innerHTML`, `__proto__`); `getTransferState` reads through `_ComponentRuntime` (page scripts in the browser, request state on the server).
- Hydration: a declarative shadow root is kept (never `attachShadow` on it) and rendered with `claimShadowRoot`, which removes the leading server `<style>`s (no template renders one): the stylesheet, adopted instead, and the `<style data-xd-style>` of the inline styles, after copying each rule into the inline style of the elements of the root holding `data-xd-style="<index>"` (`adoptServerStyles`, `utils/server-styles`, through `cssText`). An element no component adopts (the root of a page, `<style>` right before it; an island, `<style>` of the static root, which stays) does it for itself in `_connect` (`adoptHostServerStyle`). An element inside another component's shadow root waits for that component's `ClaimNodes.mount` to call its `[HYDRATE]`, unless it holds `data-xd-inputs` (interactive child of a static component); both wait for a `data-xd-hydrate` trigger (`utils/hydration-triggers`), recording and then replaying events. `data-xd-client` (`ssr: { render: false }`) has no shadow root and creates its content after waiting.
- `HYDRATION` (`utils/hydration-flag`) guards every path of the hydration in code always bundled (`CustomElement`, `_readPageTransferState`): `typeof __XAENDAR_HYDRATION__ !== 'boolean' || __XAENDAR_HYDRATION__`, which the plugin of `@xaendar/build-tools` defines as whether the project has `ssr`, so that a client-only bundle leaves the hydration out (`true` where nothing defines it: tests, server). Keep it a constant read directly in the conditions (`HYDRATION && …`, `!HYDRATION || …`): read through a function, the bundler no longer folds it. `DEV_MODE` (`utils/dev-mode`) works the same way with `__XAENDAR_DEV__`, falling back on `readDevMode()` (`process.env.NODE_ENV`) where nothing defines it. `SECURITY` (`utils/security`) reads `__XAENDAR_SECURITY__`, the defaults of `xaendar.json` where nothing defines it, the project's whoever compiled the component (libraries carry none): `_checkUrl` applies it to the URLs the templates flag, `@HostAttribute` throws for `describeUnsafeAttribute` at declaration, `registerHostAttributes` for `describeUnsafeElementAttribute` on the element (passed as the `AttributeReader`, no closure), and `applyHostAttribute` checks the URLs (`checkHostUrl`). `trustUrl`/`trustResourceUrl` return a `TrustedUrl` (a class, so `_checkUrl` tells it by `instanceof`). `sanitizeUrl`/`sanitizeResourceUrl` (`utils/sanitize-url`) apply the same checks to the URLs the code of the application uses, always, whatever `urls`/`resourceUrls` ask, giving `null` for a URL refused. Every `innerHTML` the runtime writes goes through `toTrustedHtml` of `utils/trusted-html` (policy `xaendar#template` for a standard `<template>`), never exported: a policy keeping the HTML as it is, reachable by any code, would turn an HTML never sanitized into a `TrustedHTML`; `trustedTypes` is declared in `src/globals.d.ts`.
- `CustomElement` connects through `runConnection`, so a component's error inside a `@try` is thrown by the template. `_defer` works in any project, with `@hydrate`'s triggers.
- `@xaendar/core/testing` (`src/testing/index.ts`, a `secondaryEntryPoints` sharing core's state) exports `getDeferBlocks`, `setDeferBlockBehavior` and their types; importing it sets `playthrough`, so pages outside tests register no block.
