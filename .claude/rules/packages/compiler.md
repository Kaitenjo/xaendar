# @xaendar/compiler

Turns a `.html`-like Xaendar template into a JS render-function body plus a type-check result. Depends on `common`, `types` only (**not** on `core`).

Four-stage pipeline, each stage in its own subfolder with the same layout (`<stage>/<stage>/`, `models/`, `states/`, `types/`, `utils/`):

1. `lexer`: tokenizes the raw template text.
2. `parser`: tokens → AST (`ASTNode`, `ASTNodeType`, node types like `ImportNode`).
3. `type-checker`: builds a `TypeCheckResult` from the AST plus component/directive metadata, resolved from `@import` nodes via a caller-supplied `ContextCache`.
4. `generator`: emits the JS render function body from the AST.

Entry point: `compile()` in `src/compile/compile.ts`, overloaded on `CompileOptions`:
- `baseDir` (+ optional `cache`) → only `TypeCheckResult` (editor tooling);
- `signals` → only compiled JS (module-level functions; `render` is invoked with the component bound as `this`);
- both → `{ javascript, typescript }`, computed concurrently.

`public-api.ts` also exports the generator internals `ssr-compiler` builds its server generator on: `resolveTemplateImports`, the compiler context model, `generator.utils` (expression resolution, with the `browserGlobals` option reading the browser globals through `globalThis`), `scope-generation` (`declareScope`, `declareTemplateParameters`), `catch-error-generation`, `element-namespace`, `render-target`, `symbol-imports` and their types. Change them with both generators in mind, and run the specs of `ssr-compiler` too. `getTextSeparators` decides where the server writes `<!---->` and where the client consumes it (`separated`, the last argument of `_renderText`, `_renderLiteralText`, `_renderTemplate`).

A cast `as Type` closes a whole interpolation or event parameter (`{ value() as string }`, `pick($event as MouseEvent)`): `lexExpressionText`, which reads the expressions of the interpolations and of the event parameters and the types of the casts, stops at an `as` between whitespace outside groups and literals (`peekKeywordAfterSpaces`), and the CAST state emits a CAST token with the type, then closes the interpolation (`closeInterpolation`) or the parameter. It becomes `cast` of `InterpolationNode` and `casts` (by parameter index) of `EventNode`; the type-check writes `((expression) as Type)`, the type as is and mapped (`castExpression`, `mappedInterpolation`), and no generator reads it.

The literals and the groups of the expressions and of the types are read only by `ExpressionScanner` (`models/expression-scanner`): in the lexer through `lexExpressionText` and `lexGroup`, elsewhere (parser, formatter, editor contexts) through `findEnd`, `findClosing` and `splitTopLevel` of `balanced-text.utils`. A new construct reading an expression uses them instead of a scanner of its own.

Inside an expression, `validateExpression` accepts a cast only on an argument of a call, chained ones included (`{ format(value as unknown as Date) }`, `@render row(item() as Row)`, `@if (check(value as Row))`). `resolveExpression` drops it from the JavaScript and keeps it with `preserveTypeScript`, like `!`, writing the type as is; every walker of the expressions visits their children with `forEachExpressionChild`, which leaves out the type.

The client code is the same for creating and adopting nodes: `render(nodeStrategy)` and the function of every block take the node strategy and create their context with `new _Context(parentContext, nodeStrategy)`, the one of `render` with `_ROOT_PARENT_CONTEXT` as parent (shared by every render, like the server generator). The children of an element are rendered in the context of the element: their function takes `(element, context)` and returns nothing. Only the children declaring names (the content of an element a structural directive is applied to) or changing the factory of the elements (`<svg>`, `<math>`, `<foreignObject>`, whose later blocks copy it) create a context of their own, `(element, parentContext)`, inheriting the strategy and returning it. Class bindings are emitted before the attributes, so that writing `class` finds the toggled classes.

The metadata of a component or of a directive hold `modulePath`, the file declaring its class, also when the template imports it through a barrel (`resolveExportedClass` follows the re-exports, for `getImport` of build-tools and language-core): the generated code imports it (`getDeferredModules`, `getServerDependencies`, `resolveTemplateModules` of build-tools) and the type-check references the class through it (`getOwnerType`), never through `typescriptNodes`. A component or a directive of a compiled library (`LibraryComponentMetadata`, `LibraryDirectiveMetadata` of `ComponentOrDirectiveMetadata`, told apart by `library`) has no `typescriptNodes` nor `templateUrl`: its `modulePath` is the declaration file of its module, which the type-check reads, and the generated code imports `importPath`, the path of its package (`@acme/ui/card/card.xd.component`), so the code reads `importPath ?? modulePath`.

The inputs of a component and of a directive (from the metadata of its tag, or of `@@selector`) are emitted with the input setters and the name of their property, never the alias (`exposed`: the alias of a host-directive input); the runtime never resolves an alias. A template binding an aliased input by the name of its property is a type-check error (`assertNotAliasedProperty`). `getDeferredModules` gives each `@hydrate` and each `@defer` the modules of the components and of the custom and structural directives (the cache names a directive `@@selector`) only its content renders (not the `@placeholder`, `@loading` and `@error` of a `@defer`, which render without waiting for them), emitted by `getTriggerProperties` as `load: () => Promise.all([import("…")])`, followed then only by the triggers after `prefetch` (`prefetch`, `prefetchWhen`); build-tools drops their static imports. A directive is found in its registry when an element applying it renders, after the load.

`@client` is a keyword with a block, and its `@placeholder`, read by `parseClient`, is a member of `ClientNode`, never a node of a list: the state of the `PLACEHOLDER` token only rejects an orphan one. The client code has only the content (`_client(parent, context, anchor, clientN.bind(this))`), the placeholder has none, and a listener in it is a parser error (`findEvent`). A walker of the AST reads `placeholder.children` by itself.

`@try` is a keyword with a block like `@client`, and its `@catch`, read by `parseTry`, is a member of `TryNode` (`catch: CatchNode`, with the optional `name` of the error): a `@try` without it, or an orphan `@catch` (`parseOrphanCatch`), is a parser error. The lexer reads the name between the parentheses of `@catch` as a CONDITION, validated with `assertDeclaredName`. The type-check writes a TypeScript `try`/`catch`, so the error is typed as TypeScript types the binding of a `catch` (`unknown` with `strict`), its name mapped onto the template; the generated code is `_try(parent, context, anchor, { content: tryN.bind(this), catch: catchN.bind(this) })`, the function of the `@catch` taking `error` and declaring it as a value (`context.addIdentifier('name', error)`). The root context of `render` creates its elements with `_createElement`, which constructs the components inside a `@try` (see `template-runtime.md`).

`@defer (triggers)` is followed by its `@placeholder`, `@loading` and `@error`, each one optional and declared once, in any order, read by `parseDefer` into members of `DeferNode`: an orphan `@loading` or `@error` is a parser error, and `@placeholder` reuses the `PlaceholderNode` of `@client`, its listeners allowed (the browser renders it). The parentheses of `@defer`, `@hydrate`, `@placeholder`, `@loading`, `@catch` and `@error` are optional (`lexBlockWithParameters`, which looks past the spaces with `peekMatchAfterSpaces` so that a keyword at the end of the input keeps its token): without triggers the AST keeps `triggers: []` and the generator writes `triggers: ['idle']`. `@placeholder (minimum 500ms)` and `@loading (after 100ms, minimum 1s)` are read by `readBlockParameters` (`PLACEHOLDER_PARAMETERS`, `LOADING_PARAMETERS`) into `minimum`/`after` in milliseconds (`parseDuration`: a number with `ms`, `s` or nothing); the `@placeholder` of a `@client` takes none. `@error` reads the name of its error as `@catch` does (`readErrorName`), and is type-checked as the `catch` of an empty `try`. The client code is `_defer(parent, context, anchor, { triggers, when, load, prefetch, prefetchWhen, content, placeholder, placeholderMinimum, loading, loadingAfter, loadingMinimum, error })`, the function of the `@error` taking `error`; the server writes only the `@placeholder`. The keyword context proposes, after a `@defer` and its blocks, the ones not written yet (`clientPlaceholder` tells the `@placeholder` of a `@client` apart, a block of the rendering on the server).

A `@hydrate` takes the triggers of `parseHydrateTriggers`, with `never` alone and never after `prefetch`, a `@defer` the ones of `parseDeferTriggers`, without `never`: both return `{ triggers, prefetch }`, each part split by `splitTopLevel` being `when expr` or a keyword of `DEFER_TRIGGER_KEYWORDS` with its arguments (`idle(500ms)`, `timer(2s)`, `visible(ref, { … })`, `interaction(ref)`, `hover(ref)`), after `prefetch` or not, each kind once per list; a `@hydrate` takes no element ref. The generator writes a trigger without arguments by name and the others as descriptors (`{ kind: 'hover', target: () => context.get('ref') }`, the options evaluated where the block is); `typeCheckTriggers` checks a ref with `satisfies Element` (the keyword mapped onto the ref, where TypeScript reports it) and the options with `satisfies Omit<IntersectionObserverInit, 'root'>`, and `checkVariableOrder` the options and `when`, not the ref, read after the render. `getTriggerContext` proposes the triggers and the parameters in the editor, and `getExpressionContext` leaves the keywords to it (`isTriggerExpression`). `checkTriggerTargets` rejects `visible`, `interaction` and `hover` without an element ref, the ones after `prefetch` too, on a `@hydrate` whose content is sure to render no element, and on a `@defer` whose `@placeholder` is (or without one), and `checkServerBlocks` rejects `@hydrate` and `@client` when the `ssr` option is `false` (`undefined` means not known, and they pass): they run as checks of the whole template, like `checkVariableOrder`, so that the editor keeps checking the content of the blocks. `extractComponentsMetadataFromSourceFile` reads `ssr: { render: false }` into `clientOnly`, with the trigger next to it: `findWebComponentErrors` rejects what it cannot read, and the `ssr` option when its `ssr` argument is `false` (`undefined` means not known). It is the single source of the errors of a `@WebComponent` the source file alone tells, with the span of each one, for the build (`transform`) and the editor (`getComponentDiagnostics`), and `describeSelectorConflict` gives both the message of a selector used twice. `generatorContext.getClientComponent` gives these components to the server generator.

`findComponentLogic` and `findModuleLogic` read what a class and its module do in the browser, for the analysis of the static components in `build-tools`. They prove a component static: what they cannot read counts as logic, and each case returns a reason, shown by the report of the build.

The manifest of a built library (`xaendar-manifest.json`) has its types in `types/library-manifest/` (`LibraryManifest`, one `LibraryManifestDeclaration` per exported component or directive, keyed `<module>#<ClassName>`, with every input and event and its `type`). `utils/library-manifest` writes a declaration from the metadata (`toLibraryDeclaration`) and reads the `import('…')` of the types (`listTypeReferences`, `mapTypeModules`, which rewrites the absolute paths of the sources as paths relative to the package).

`toLibraryMetadata` is the inverse of `toLibraryDeclaration`: the modules of the package the types reference become absolute paths, and every component of a package without `ssr` gets `clientOnly`. `utils/package-libraries` reads the packages: `readLibraryMetadata` the component or the directive a declaration file exports under a name (the `exports` of the `package.json` lead the file to a path, the manifest that path to a declaration), `readLibraryClass` one by the declaration file of its class (the `hostDirectives` of a component, `extractHostDirectiveBindings`), `readLibrary` a package once while its `package.json` keeps its mtime, rejecting a manifest of another `schemaVersion` and a `@xaendar/core` (found from the package as Node finds it) of another major version or older than `xaendar`, and `findPackageLibraries` the libraries a project depends on, and their own ones.

The variables of a template (the item and the implicit variables of a `@for` and their aliases, a `@let`, the parameters of a `<template>`) are values: declared with the kind `variable` (`IdentifierKind`) and read as `context.get('name')`, never called. `resolveExpression` lists the ones an expression reads (`variables`), and the client generator passes their names to the helper of the binding as its last argument, a constant of the module per list (`getReads`, `readsDeclarations`: `const _reads0 = ['row'];`), so that the runtime runs the binding again when its scope changes one of them (see `template-runtime.md`). An expression reading no name at all is constant (`isConstantExpression`): an attribute or a class binding is written with `_setExpression*` and a `@let` as a value; any other one with `_setReactive*`, the runtime deciding whether it is an effect. The type-check declares each variable with the type of its value (`typeof $$item`, `number` and `boolean` for the implicit ones, the inferred type of a `@let`, the type of a parameter) and records the calls of the variables (`recordVariableCall`, `variableCalls` of the result): `describeVariableCall` turns the error 2349 TypeScript reports on one into the message telling to remove the parentheses, for the build (`describeDiagnostic`) and the editor (`getTemplateDiagnostics`), while the call of a variable holding a function is valid.
