# @xaendar/compiler

Turns a `.html`-like Xaendar template into a JS render-function body plus a type-check result. Depends on `common`, `types` only (**not** on `core`).

Four-stage pipeline, each stage in its own subfolder with the same layout (`<stage>/<stage>/`, `models/`, `states/`, `types/`, `utils/`):

1. `lexer`: tokenizes the raw template text.
2. `parser`: tokens → AST (`ASTNode`, `ASTNodeType`, node types like `ImportNode`).
3. `type-checker`: builds a `TypeCheckResult` from the AST plus component/directive metadata, resolved from `@import` nodes via a caller-supplied `ContextCache`.
4. `generator`: emits the JS render function body from the AST.

Entry point: `compile()` in `src/compile/compile.ts`, overloaded on `CompileOptions`:
- `baseDir` (+ optional `cache`) → only `TypeCheckResult` (editor tooling);
- `signals` → only compiled JS (module-level functions; `render` is invoked with the component bound as `this`);
- both → `{ javascript, typescript }`, computed concurrently.

`public-api.ts` also exports the generator internals `ssr-compiler` builds its server generator on: `resolveTemplateImports`, the compiler context model, `generator.utils` (expression resolution, with the `browserGlobals` option reading the browser globals through `globalThis`), `scope-generation` (`declareScope`, `declareTemplateParameters`), `catch-error-generation`, `element-namespace`, `render-target`, `symbol-imports` and their types. Change them with both generators in mind, and run the specs of `ssr-compiler` too. `getTextSeparators` decides where the server writes `<!---->` and where the client consumes it (`separated`, the last argument of `_renderText`, `_renderLiteralText`, `_renderTemplate`).

A cast `as Type` closes a whole interpolation or event parameter (`{ value() as string }`, `pick($event as MouseEvent)`): `lexExpressionText`, which reads the expressions of the interpolations and of the event parameters and the types of the casts, stops at an `as` between whitespace outside groups and literals (`peekKeywordAfterSpaces`), and the CAST state emits a CAST token with the type, then closes the interpolation (`closeInterpolation`) or the parameter. It becomes `cast` of `InterpolationNode` and `casts` (by parameter index) of `EventNode`; the type-check writes `((expression) as Type)`, the type as is and mapped (`castExpression`, `mappedInterpolation`), and no generator reads it.

The literals and the groups of the expressions and of the types are read only by `ExpressionScanner` (`models/expression-scanner`): in the lexer through `lexExpressionText` and `lexGroup`, elsewhere (parser, formatter, editor contexts) through `findEnd`, `findClosing` and `splitTopLevel` of `balanced-text.utils`. A new construct reading an expression uses them instead of a scanner of its own.

Inside an expression, `validateExpression` accepts a cast only on an argument of a call, chained ones included (`{ format(value as unknown as Date) }`, `@render row(item() as Row)`, `@if (check(value as Row))`). `resolveExpression` drops it from the JavaScript and keeps it with `preserveTypeScript`, like `!`, writing the type as is; every walker of the expressions visits their children with `forEachExpressionChild`, which leaves out the type.

The client code is the same for creating and adopting nodes: `render(nodeStrategy)` and the function of every block take the node strategy and create their scope with `_scope(parentContext, _layoutN, nodeStrategy)`, the one of `render` with `null` as parent and the component (`_scope(null, _layout0, nodeStrategy, this)`), which the scopes inside it inherit (the `COMPONENT` slot). The layout of a scope (`GeneratorContext.declareLayout`, `{ size, nodes, bindings?, sites?, containers?, variables? }`, identical layouts sharing one `_layoutN` constant) is known once its body is generated: `SCOPE_HEADER` slots (`costants/scope-header.costant.ts`, equal to core's `HEADER`: change both together), then one slot per variable it declares (`addIdentifier` gives the slot and an identifier unique in the template), then one per node at its top (`allocateNodeSlot`, written as `slot` in the constant of the element or of the block), then the slots of its bindings (`declareBinding`), then the areas of its branches rendered inline, then one container of `CONTAINER_SLOTS` (3, `costants/container-slots.costant.ts`, equal to core's) slots per block it renders, the ones rendered into its elements included (`allocateContainer`, written as `container` in the constant, left out for the first, `appendContainer`; the children of an element opening a namespace give it to the nearest scope opening a runtime scope). The layouts are declared once every function is generated (`LAYOUT_PLACEHOLDER` in the line creating the scope), since the children of an element are generated after it, and their blocks take containers of its scope. The content of an element a structural directive is applied to opens a runtime scope when it declares names or renders a block (`rendersBlock`, kind `scope` instead of `declarations`), held by the container of the scope of the element (`STRUCTURAL_LAYOUT`). A variable is read as `_read(context, depth, slot)` (`CompilerContext.addressOf`, `depth` counting the scopes up the chain of the declaring scopes), never by name: the runtime has no lookup by name. The children of an element are rendered in the context of the element: their function takes `(element, context)` and returns nothing. Only the children declaring names (the content of an element a structural directive is applied to) create a context of their own, `(element, parentContext)`, inheriting the strategy and returning it. The namespace of an element, known from its place in the template (`GeneratorContext.namespace`, `getElementNamespace`), is written in its constant (`namespace: 1` SVG, `namespace: 2` MathML, nothing for HTML, `appendNamespace`), in the blocks and the templates of an `<svg>` too: no code changes how the elements are created, and the children of an `<svg>`, a `<math>` or a `<foreignObject>` need no context.

What the generated code passes to the runtime never changes from an instance of the template to another, so it is declared once in the module: every element and block is described by a constant (`GeneratorContext.declareConstant`: `td0$element` for `_renderElement`, `div0__if0$if`, `td0__switch0$switch`, `table0__for0$for`, `div0__render1$render`, `div0__try0$try`, `…$defer`, `…$hydrate`, `template_row_12$template`, the variables of a `@for`), written after the `_readsN`, and every expression (texts, attributes, inputs, classes, conditions, the expression of a `@switch`, the items and the track of a `@for`, the arguments of a `@render`, `@let`, the default values of the parameters, the event handlers, `when`, the targets of the triggers) is a function of the module (`GeneratorContext.declareFunction`, `declareExpression` of `utils/module-code`), written after the functions of the blocks, which receives the context (an event handler the context, then `$event`; the track the context, then the item and the implicit variables, its context named `__context` when one of them is named `context`) and reads the members as `this`: the runtime calls it with `context[COMPONENT]`. A name is the one of the element or of the block, `$` and the role (`tr0$class`, `td0$on_click`, `div0__if0$condition`, `span0$text0`), a number appended when taken. The functions of the blocks are referenced as they are, never `.bind(this)`: they read nothing through `this`. The last node of its parent (`isLastRenderedChild` of `utils/block-position`: only `@import`, `<template>` and `@let` follow it) is passed `last` by `Generator` when the function holding it has no anchor (the root, the children of an element, the content of a block itself `last`): a block there writes `last: true` in its constant (`appendBlockPosition`; an element only when it applies structural directives, `_client` as its last argument) and gives its content functions no anchor (`getContentAnchor`), so that their own last block is `last` too, while the body of a `@for` and the content of a template keep `anchor`. The server generator reads the same function (`ServerParent.end`): change both together. A list a configuration does not declare is left out. The runtime only reads the constants: the state of a block lives in its container (three slots of its scope, see `template-runtime.md`), the one of a conditional binding in its `ConditionalBindingRun`. Every binding of a compiled scope is a binding site, declared with `GeneratorContext.declareBinding` (`update`, `effect`, `target` appended, slots counted per runtime scope, `layout.bindings`/`layout.sites` written by `declareLayout`); a context of kind `runtime` (the owner of an element with structural directives, the branches of a conditional binding) reserves none. `@if`/`@switch` are declared with `declareBlock`, their `branches` last: a branch passing `rendersInline` gets a context of kind `inline` (`describeBranch`), which opens no runtime scope (its reads count the depth of the scope holding the block), counts its nodes, bindings and cleanup slot (`reserveCleanup`, for listeners) from 0 in one counter, and is generated as `(key, context, anchor?)` creating no scope; the constant of such a block is written by `declareLayout` of the scope holding it, which places one area per block after the bindings, as large as its largest inline branch (`base`, `size`, `nodes`, `sites`, `cleanup` of the branch). The server generator follows the same rule for its descriptors (see `ssr-compiler.md`).

The metadata of a component or of a directive hold `modulePath`, the file declaring its class, also when the template imports it through a barrel (`resolveExportedClass` follows the re-exports, for `getImport` of build-tools and language-core): the generated code imports it (`getDeferredModules`, `getServerDependencies`, `resolveTemplateModules` of build-tools) and the type-check references the class through it (`getOwnerType`), never through `typescriptNodes`. A component or a directive of a compiled library (`LibraryComponentMetadata`, `LibraryDirectiveMetadata` of `ComponentOrDirectiveMetadata`, told apart by `library`) has no `typescriptNodes` nor `templateUrl`: its `modulePath` is the declaration file of its module, which the type-check reads, and the generated code imports `importPath`, the path of its package (`@acme/ui/card/card.xd.component`), so the code reads `importPath ?? modulePath`.

The inputs of a component and of a directive (from the metadata of its tag, or of `@@selector`) are emitted with the input setters and the name of their property, never the alias (`exposed`: the alias of a host-directive input); the runtime never resolves an alias. A template binding an aliased input by the name of its property is a type-check error (`assertNotAliasedProperty`). `getDeferredModules` gives each `@hydrate` and each `@defer` the modules of the components and of the custom and structural directives (the cache names a directive `@@selector`) only its content renders (not the `@placeholder`, `@loading` and `@error` of a `@defer`, which render without waiting for them), emitted by `getTriggerProperties` as `load: x$load`, a function of the module returning `Promise.all([import("…")])`, followed then only by the triggers after `prefetch` (`prefetch`, `prefetchWhen`); build-tools drops their static imports. A directive is found in its registry when an element applying it renders, after the load.

`@client` is a keyword with a block, and its `@placeholder`, read by `parseClient`, is a member of `ClientNode`, never a node of a list: the state of the `PLACEHOLDER` token only rejects an orphan one. The client code has only the content (`_client(parent, context, anchor, clientN)`), the placeholder has none, and a listener in it is a parser error (`findEvent`). A walker of the AST reads `placeholder.children` by itself.

`@try` is a keyword with a block like `@client`, and its `@catch`, read by `parseTry`, is a member of `TryNode` (`catch: CatchNode`, with the optional `name` of the error): a `@try` without it, or an orphan `@catch` (`parseOrphanCatch`), is a parser error. The lexer reads the name between the parentheses of `@catch` as a CONDITION, validated with `assertDeclaredName`. The type-check writes a TypeScript `try`/`catch`, so the error is typed as TypeScript types the binding of a `catch` (`unknown` with `strict`), its name mapped onto the template; the generated code is `_try(parent, context, anchor, tryN$try)`, the constant `{ content: tryN, catch: catchN }`, the function of the `@catch` taking `error` and writing it in the slot of its name (`context[slot] = error;`). The HTML elements are created with `_createElement`, which constructs the components inside a `@try` (see `template-runtime.md`).

`@defer (triggers)` is followed by its `@placeholder`, `@loading` and `@error`, each one optional and declared once, in any order, read by `parseDefer` into members of `DeferNode`: an orphan `@loading` or `@error` is a parser error, and `@placeholder` reuses the `PlaceholderNode` of `@client`, its listeners allowed (the browser renders it). The parentheses of `@defer`, `@hydrate`, `@placeholder`, `@loading`, `@catch` and `@error` are optional (`lexBlockWithParameters`, which looks past the spaces with `peekMatchAfterSpaces` so that a keyword at the end of the input keeps its token): without triggers the AST keeps `triggers: []` and the generator writes `triggers: ['idle']`. `@placeholder (minimum 500ms)` and `@loading (after 100ms, minimum 1s)` are read by `readBlockParameters` (`PLACEHOLDER_PARAMETERS`, `LOADING_PARAMETERS`) into `minimum`/`after` in milliseconds (`parseDuration`: a number with `ms`, `s` or nothing); the `@placeholder` of a `@client` takes none. `@error` reads the name of its error as `@catch` does (`readErrorName`), and is type-checked as the `catch` of an empty `try`. The client code is `_defer(parent, context, anchor, deferN$defer)`, the constant `{ triggers, when, load, prefetch, prefetchWhen, content, placeholder, placeholderMinimum, loading, loadingAfter, loadingMinimum, error }`, the function of the `@error` taking `error`; the server writes only the `@placeholder`. The keyword context proposes, after a `@defer` and its blocks, the ones not written yet (`clientPlaceholder` tells the `@placeholder` of a `@client` apart, a block of the rendering on the server).

A `@hydrate` takes the triggers of `parseHydrateTriggers`, with `never` alone and never after `prefetch`, a `@defer` the ones of `parseDeferTriggers`, without `never`: both return `{ triggers, prefetch }`, each part split by `splitTopLevel` being `when expr` or a keyword of `DEFER_TRIGGER_KEYWORDS` with its arguments (`idle(500ms)`, `timer(2s)`, `visible(ref, { … })`, `interaction(ref)`, `hover(ref)`), after `prefetch` or not, each kind once per list; a `@hydrate` takes no element ref. The generator writes a trigger without arguments by name and the others as descriptors (`{ kind: 'hover', target: deferN$hover_target }`, a function of the module reading the ref; the options written in the constant when they read no name, a function of the module evaluated when the trigger is armed otherwise); `typeCheckTriggers` checks a ref with `satisfies Element` (the keyword mapped onto the ref, where TypeScript reports it) and the options with `satisfies Omit<IntersectionObserverInit, 'root'>`, and `checkVariableOrder` the options and `when`, not the ref, read after the render. `getTriggerContext` proposes the triggers and the parameters in the editor, and `getExpressionContext` leaves the keywords to it (`isTriggerExpression`). `checkTriggerTargets` rejects `visible`, `interaction` and `hover` without an element ref, the ones after `prefetch` too, on a `@hydrate` whose content is sure to render no element, and on a `@defer` whose `@placeholder` is (or without one), and `checkServerBlocks` rejects `@hydrate` and `@client` when the `ssr` option is `false` (`undefined` means not known, and they pass): they run as checks of the whole template, like `checkVariableOrder`, so that the editor keeps checking the content of the blocks. `extractComponentsMetadataFromSourceFile` reads `ssr: { render: false }` into `clientOnly`, with the trigger next to it: `findWebComponentErrors` rejects what it cannot read, and the `ssr` option when its `ssr` argument is `false` (`undefined` means not known). It is the single source of the errors of a `@WebComponent` the source file alone tells, with the span of each one, for the build (`transform`) and the editor (`getComponentDiagnostics`), and `describeSelectorConflict` gives both the message of a selector used twice. `generatorContext.getClientComponent` gives these components to the server generator.

`findComponentLogic` and `findModuleLogic` read what a class and its module do in the browser, for the analysis of the static components in `build-tools`. They prove a component static: what they cannot read counts as logic, and each case returns a reason, shown by the report of the build.

The manifest of a built library (`xaendar-manifest.json`) has its types in `types/library-manifest/` (`LibraryManifest`, one `LibraryManifestDeclaration` per exported component or directive, keyed `<module>#<ClassName>`, with every input and event and its `type`). `utils/library-manifest` writes a declaration from the metadata (`toLibraryDeclaration`) and reads the `import('…')` of the types (`listTypeReferences`, `mapTypeModules`, which rewrites the absolute paths of the sources as paths relative to the package).

`toLibraryMetadata` is the inverse of `toLibraryDeclaration`: the modules of the package the types reference become absolute paths, and every component of a package without `ssr` gets `clientOnly`. `utils/package-libraries` reads the packages: `readLibraryMetadata` the component or the directive a declaration file exports under a name (the `exports` of the `package.json` lead the file to a path, the manifest that path to a declaration), `readLibraryClass` one by the declaration file of its class (the `hostDirectives` of a component, `extractHostDirectiveBindings`), `readLibrary` a package once while its `package.json` keeps its mtime, rejecting a manifest of another `schemaVersion` and a `@xaendar/core` (found from the package as Node finds it) of another major version or older than `xaendar`, and `findPackageLibraries` the libraries a project depends on, and their own ones.

The body of a `@for` creates only the variables it reads (`getReadForVariables` of `generator/utils/for-reads`, shared with `ssr-compiler`), and only they are declared in the context of the body. Both generators write them once per template, as a constant of the module (`const for0Variables = { used: […], names: […] };`, `writeIterationVariables`, declared with `declareConstant`), passed to `_iterationVariables` and, on the client, to `_for`, which updates the values of a reused item by their position in `used` and refreshes its context; a body reading none has no constant. The function of the body returns its context, the only object a `@for` keeps per item. The analysis walks the whole body with `walkTemplate` (`utils/template-walker`) and `collectReads` (`utils/expression-reads`), plus the texts the generators resolve or write as is (the handlers of the events, the callee of `@render`, the conditions of `@case`): it may be wider than needed, never narrower, so a name declared again inside the body still counts. A new construct holding an expression or code is visited by `walkTemplate`.

The variables of a template (the item and the implicit variables of a `@for` and their aliases, a `@let`, the parameters of a `<template>`) are values: declared with the kind `variable` (`IdentifierKind`) and read as `_read(context, depth, slot)`, never called. `resolveExpression` lists the ones an expression reads (`variables`), and the client generator passes their identifiers, unique in the template, to the helper of the binding as its last argument, a constant of the module per list (`getReads`, `readsDeclarations`: `const _reads0 = [0];`), so that the runtime runs the binding again when its scope changes one of them (see `template-runtime.md`). An expression reading no name at all is constant (`isConstantExpression`): an attribute or a class binding is written with `_setExpression*` and a `@let` as a value; any other one with `_setReactive*`, the runtime deciding whether it is an effect. The type-check declares each variable with the type of its value (`typeof $$item`, `number` and `boolean` for the implicit ones, the inferred type of a `@let`, the type of a parameter) and records the calls of the variables (`recordVariableCall`, `variableCalls` of the result): `describeVariableCall` turns the error 2349 TypeScript reports on one into the message telling to remove the parentheses, for the build (`describeDiagnostic`) and the editor (`getTemplateDiagnostics`), while the call of a variable holding a function is valid.

A `<template>` is the declaration of a template only when its first item is a name directly followed by `(` (`expectsTemplateDeclaration`): `<template row>`, `<template id="x">` are standard `<template>` elements, an `ElementNode` whose `content` holds the HTML of its static content (`serializeTemplateContent` of `parser/utils/template-content`, the escaping of the server), its children kept for the editor: the generators write `content` instead of generating them, the type-check skips them, and a binding, an event, a ref, a directive, a block or a `<template name()>` in the content, or a `shadowroot*` attribute on the element, is a parser error. A template name is an identifier of kind `template`: read in an expression it is `_templateRef(context, depth, constant)`, a `TemplateRef`. `@render` calls the name of a template visible in scope (`getRenderedTemplate`, which checks its namespace) or any expression (`RenderNode.calleeExpression`; the lexer reads a chain of names, `.`/`?.` accesses, `[key]` and calls up to the last group of parentheses, which are the arguments): the client constant gets `ref` (a function of the module), the server calls `_ssrRenderTemplateRef`, and the type-check writes `__render(expression, count)(args)` against `__Template<Params>`, shaped like `TemplateRef` of core (`{ readonly __template: (...params) => void }`) and accepting `null`/`undefined`; the walkers visit the expression like the arguments. The `<template name()>` children of a component's element are passed to it (`mapContentTemplates` of `utils/content-templates`, shared with `ssr-compiler`: `templates: [{ name, template }]` in its constant), an error on an element with structural directives.

`@for` iterates any value `_forItems` of core accepts (an array, a number, any iterable but a string): the type-check passes the iterable to `FOR_ITERABLE`, `<T extends number | Iterable<unknown>>(iterable: T & (T extends string ? never : unknown))`, so `for…of` types the entries of a `Map`, and a string is reported as not assignable to `never`. The implicit variables are listed once, `FOR_IMPLICIT_VARIABLES` (`$index`, `$first`, `$last`, `$even`, `$odd`, `$count`), in the order of the parameters of the track after the item. `} @empty { … }` (`TokenType.EMPTY`, read with optional parentheses that the parser rejects, an orphan one rejected by `parseOrphanEmpty`) is `ForNode.empty`, an `EmptyNode` whose content is a scope of its own in the enclosing one, without the variables of the loop: the client constant names its function (`empty: for0Empty`, anchor `getContentAnchor(last)`), the server writes it between the markers when there are no items, the type-check checks it in a block after the loop, and every walker visits it with the enclosing variables.

A two-way binding, `[(value)]="count"`, is lexed as an attribute whose name holds its parentheses (`lexAttribute`, `readTwoWayName` of the layout of the formatter) and parsed by `parseTwoWayBinding` (before `parseBracketBinding`, on elements, branches and in the parentheses of a directive) into the two nodes it stands for, both marked `twoWay`: the attribute `value` whose interpolation is `count()` and the event `valueChange` calling `count.set($event.detail)`, both named by the span of `value`, the handler by the span of `count` (an identifier or a chain of accesses, no call nor `?.`). Generators, type-check and walkers then treat them as written by hand; only the checks read `twoWay`: `assertTwoWayBindable` (the input and its event of change, `toModelChangeEvent` of `@xaendar/common`) and native elements in the type-check, an attribute matching no input in both generators; language-core leaves the event out of the semantic tokens and of the definitions, and `getBindingContext` gives `kind: 'twoWay'` after `[(`. `@Model`/`@Model.required` are read with `@Property` (`isPropertyDecorator`): a model adds its property and the event `<alias or name>Change` typed as the property, sharing its declaration, removed with it when a subclass overrides the accessor.

A key event, `(keydown.enter)`, `(keyup.control.shift.z)`, `(keydown.code.keya)`, keeps its `name` as written, and `parseEvent` reads its `key` with `parseKeyEvent` of `@xaendar/common` (shared with `@HostListener` and language-core): a `KeyEventFilter`, the event (`keydown`/`keyup`), the key in lowercase, the bits of `KEY_MODIFIERS` and `code`; only `keydown.*`/`keyup.*` are key events, a modifier that does not exist, a missing key or a part named twice is thrown on the span of the name. `mapEvents` listens to the event and writes the filter into the handler, a function of the module (`if (_isKey($event, 'enter', 0)) this.save();`, `_isKey` of core), and a key event making the same call as the last listener of its event, filtered too, joins it, its key added to the condition with `||` (`TemplateListenerCode`). N.B. Deliberate, to save memory: the filter is never kept in the listener, so a filtered listener costs what any listener costs, and the keys joined cost one listener and one registration per element; a listener without filter and different calls are never joined, so that listeners are called in the order written. The type-check types `$event` by the event (`HTMLElementEventMap['keydown']`, never an `@Event` named like the key event), mapping the name quoted in it onto the beginning of the name; `ssr-compiler` registers the event in the contract (`keydown`); `getTemplateKeyEventCompletions` of language-core proposes the common keys, the modifiers not yet written and `code` after `(keydown.`/`(keyup.`, the modifiers alone after `code.`.

A native event (`typeCheckNativeEvent`: on a native element, or not declared by the `@Event`s of a component or a directive) types `$event` as `(Map extends { 'name': infer Event } ? Event : Event)`, never an error: an event the map does not declare may bubble up to the element. With `strictEvents` (`CompileOptions`, default `true`, kept by the outermost `TypeCheckContext`) its name is checked on a line of its own, `'name' satisfies keyof HTMLElementEventMap;`, and recorded (`recordEventCheck`, `eventChecks` of the result: the span of the binding, of the name and the message); `findEventCheck` turns the error 1360 on it into a warning on the name, for the build (`describeEventCheckDiagnostic`) and the editor (`getTemplateDiagnostics`). Key events and the elements of `customElements` (`$event` `any`) get no check.

Bindings in brackets are parsed by `parseBracketBinding`: `[class.name]` into a `ClassBindingNode`, `[style.name]` into a `StyleBindingNode` (`property` in kebab-case, camelCase converted; `unit` after a last `.` matching `[a-z]+|%`; a custom property `--name` as written), each in its own list of the element or the branch (`styleBindings`). The `class` and the `style` of an element or of a branch are mapped once each (`mapBindings`, `mapStyling`, with `describeStyling` and `splitStylingAttributes` of `generator/utils/styling`, shared with `ssr-compiler`), before the other attributes: the static string parsed at compile time (`text`, `statics`), the expression of the string, the keys bound alone (`keys`, `values`, `units`), one binding site per attribute (`declareBinding(…, indexed)`: target and value slots), unless a component declares an input with that name. The element writes `styling` (flags of `stylingFlags`) when another source may write the same attribute, a branch its own `styling`, and the directives of an element applying more than one their `order` (`orderDirectives`, by position in the source). A unit must be one of `CSS_UNITS` of `@xaendar/common`; the type-check checks a value with `satisfies number | null | undefined` for a property with a unit, `string | number | null | undefined` otherwise.
