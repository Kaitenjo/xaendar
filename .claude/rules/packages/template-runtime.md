# Template runtime model

Compiled templates don't produce a virtual tree: they produce imperative JS that mounts real DOM nodes through `core`'s `_Context`/`mountNode`/`createAnchor` (`packages/core/src/utils/context/context.util.ts`).

- Each `_Context` is one lexical scope (root component, or a nested scope from `@for`/`@if`). It holds its declared identifiers, owned DOM nodes, cleanup callbacks and the bindings reading its variables (see below), and looks up identifiers in parent scopes via `_parent`. The compiled code creates it for the number of variables its scope declares (`new _Context(parentContext, nodeStrategy, count)`, written by `createContext` of the compiler from `identifierCount` of the generator context, by both generators): up to 16 they are kept in an array of that size alternating names and values, beyond in a `Map`; a context created without the number (by the runtime, or by code compiled before) grows the array one variable at a time. An event handler is a function of the module of the template, bound by a `TemplateListener` with the context it is declared in: it reads the variables through the context when the event fires, so it sees their current values.
- The bindings of a template (texts, attributes and classes, conditional bindings, the conditions of `@if` and `@switch`, the items of `@for`, the arguments of `@render`, the values of `@let` and the default values of the parameters, `when` of `@defer` and `@hydrate`) go through `_bindEffect(context, callback, first, second?, third?, reads?)` (`signals/effect`): a callback declared once at module level and its arguments, never a closure, the expression of the template being one of the arguments: a function of the module of the template, kept with the context and called `expression.call(context.component, context)`. What the generated code passes (the configuration of an element, of a block, of a `@for`, a template) is a constant of its module (`RenderElement`, `BlockConfig`, `ForConfig`, `RenderTemplateConfig`, `_Template`), shared by every instance and never written: the state stays in the run objects. Listeners are `TemplateListener` objects (`handleEvent`, `dispose`), the unbinding of a branch one `AttributeUnbinding`, the branches of a conditional binding applied by a function of the module receiving their target (`ElementBinding`, a directive, the collector of the structural directives). A template is held by its scope as its constant, and `_renderTemplate` finds that scope with `ownerOf`. Its first run, synchronous, happens in the `Computed` of an `EffectNode` (`_runBinding`): when it reads at least one signal the node becomes the effect of the binding, watched by a `Watcher` of its own, otherwise it is dropped. The variables of the template (the item and the implicit variables of a `@for`, a `@let`, the parameters of a template) are plain values in the context, never signals: a binding reading some of them gets `reads`, their names, from the compiler, and is kept in its context as a `Binding` (`addBinding`), whatever it read. A scope whose variables change writes them with `update` (`true` only when the value differs, by `Object.is`) and calls `refresh(names)`: every binding of the context and of its descendants reading one of the names runs again (`rerunBinding`), deciding again whether it is an effect (a binding no longer reading a signal drops its effect, one starting to read one gets it), its error reported in a microtask. A refresh started during another one adds its names to the outer ones, and the pass mark (`_pass`) keeps a context from being refreshed twice in a pass. `_for` refreshes the context of a reused item with the variables that changed before moving its nodes, `_renderTemplate` an instance with the parameters that changed, and `_let` its scope with its name (`propagate`, joining the refresh in progress, if any). A signal change runs only the effects reading it, never a refresh.
- An element does not open a context: `renderElementChildren` renders its children in the context of the element, so their effects and listeners are cleared with it, and creates a child context only when their strategy differs (`nodeStrategy.children`, an element created in a hydration) or when the generated function creates one (see `compiler.md`). A context tracks only the nodes at the top of its block, all rendered into the same node: `trackNode` skips the nodes rendered into an element while `renderChildren` renders its children in that same context (a variable of the module, rendering being synchronous), since they are removed with the element. `getNodes()` (`_for` moving an item, `_defer`, `createComponent`) relies on it: never track a node rendered into an element of the template.
- `createAnchor` places a `Comment` node as a stable insertion point for structural directives: dynamic content is always inserted via `insertBefore(node, anchor)`, independently of sibling constructs.
- `unlisten()` destroys a context: recursively disposes children, detaches listeners, removes owned nodes. This is what makes per-signal DOM updates surgical without a virtual-DOM diff.
- The helpers never create nodes directly: they ask `context.nodeStrategy`, a `NodeStrategy` (`CREATE_NODES`, or `ClaimNodes` adopting the HTML of the server during the first render of a component rendered on the server). No helper branches on hydration: the strategy is chosen once per component (`CustomElement`) and once per block (`adopt`/`adoptItems` at the first run of `_if`, `_for`, structural elements). `ClaimNodes.end` gives `CREATE_NODES` to the whole tree of contexts (`setNodeStrategy`), so every later run reads `context.nodeStrategy` and no helper names the constant. Effects write the DOM only when the value differs (`updateAttribute`, the text compare), so an adopted node is not written again.
- `_hydrate` (`@hydrate`): with the HTML of the server, `skip` passes over its content, owned by the context and inert (events recorded, its code not running) until a trigger fires, then a `ClaimNodes(host, true)` started at its first node adopts it and the events are replayed; `visible`, `interaction` and `hover` become `idle` without elements to watch, which only a block rendering nothing in the end reaches: content sure to render no element is a compile error (`checkTriggerTargets`). The triggers after `prefetch` load the modules once (`loaded` memoized, a failed prefetch silent), `prefetch interaction` firing through the events recorded, like `interaction`; `hover` listens in the capture phase, armed before the recording stops the events (in `deferElementHydration` too). Without the HTML of the server the triggers do not count: the content renders with `CREATE_NODES` once its modules are loaded. An element adopted declaring `data-xd-hydrate` waits for that trigger (`deferElementHydration`), unless it is in the content of a `@hydrate`. `never` returns before the triggers are armed and the events recorded, which would stop them for good: a `@hydrate (never)` keeps its nodes owned by the context and never loads its modules, and an element declaring it never hydrates, unless a `@hydrate` holding it does: the template always wins over the decorator (`ClaimNodes.mount`). A hydration that waited for a trigger is quiet: what differs from the HTML of the server is rendered again without warnings, in the components it adopts too.
- The event contract: `renderToString` writes `eventContract` (`packages/ssr/src/utils/event-contract`) as an inline script after the root of the page. It needs no runtime, records on the document and on every shadow root (`change` and `submit` are not `composed`), and leaves on `window` the queue, under the symbol `_EVENT_CONTRACT_KEY` (`Symbol.for('xaendar.eventContract')`, which the script gets again from its description: `packages/core/src/window.d.ts` declares it on `Window`, so no cast is needed to read it: the projects compiling the sources of core include it next to `globals.d.ts`). The first use of the queue stops it (`takeContractEvents`), or a listener left there would record again what the components handle, replaying it twice. `recordEvents` takes the events on its targets, and a caller with `interaction` fires for them in a microtask; the end of a hydration schedules `replayContractEvents`, a microtask, so that the listeners of a whole tree hydrated in one tick are bound. What goes through an element still waiting stays (`WAITS_FOR_HYDRATION`). Nothing of the triggers reaches the HTML: nothing can hydrate before the runtime. `data-xd-submit` is the only mark, for the one decision that cannot wait: preventing a submission.
- `_client` (`@client`): `replace` removes the `@placeholder` the server rendered, moving the position past its anchor, and the content is created with `CREATE_NODES`, in the same pass of the hydration, without warnings; `CREATE_NODES.replace` does nothing, so no helper branches on it. Inside a `@hydrate` or a component with a trigger it runs when they hydrate. A component of the placeholder is removed without ever hydrating: `disconnectedCallback` then runs no hook, disposing only what its constructor created.
- `_try` (`@try`): renders the content in a holder context, inside a scope (`openTryScope`, `utils/try-scope`) collecting every context created until the content returns, the ones of the components it renders included, since a block registers its context in its parent only once rendered: when the first render throws, they are cleared in creation order (a component is removed, running `onDestroy`, before its own contexts are disposed), and the `@catch` renders with the error, outside the scope. Only the first render is caught, the code of the components the template creates included, as JavaScript catches the functions a `try` calls: inside a scope, `_createElement` constructs a defined custom element with `new` (`document.createElement` reports the error of the constructor instead of throwing it), and `renderElement` mounts through `connectChild`, which throws the error the component handed it from its `connectedCallback` (`runConnection`; the browser reports what a connection callback throws). A component inserted by other code (`appendChild` in `onInit`) runs outside the scope, as the browser reports its error. In a hydration, the classes are defined, and the adopted elements constructed, before the template runs: a constructor throwing there is not caught. `trackNode` removes only a node inserted, as the element whose bindings threw. With the HTML of the server (`<!--xd-t:0-->` content, `<!--xd-t:1-->` catch): the content is adopted, and when it throws the rest is emptied with a warning (`adopt(…, '1')`); a `@catch` of the server is removed silently (`replace`, whose position is past the anchor, so no `close` after it), since its error does not reach the browser, and the block renders from scratch.
- `_defer` (`@defer`): renders its `@placeholder` (with `adopt(…, '')`, so it adopts the one the server rendered between `<!--xd-d-->` and `<!--/xd-d-->`, its listeners bound, then `close`), arms the triggers and the ones after `prefetch` with `armTriggers` of `utils/hydration-triggers` in a microtask, once the template holding the block is rendered (an element ref a trigger names is read then, `target()`), and `when` and `prefetchWhen` with effects, and replaces the part shown with `CREATE_NODES` (a trigger always fires after the hydration): the `@loading` while `load()` runs, then the content, or the `@error` with the error, or, without one, the `@placeholder` again, the error logged. `load` is memoized: the prefetch starts it, silent when it fails, and the trigger rendering the content waits for it. The times: the `@placeholder` stays at least `placeholderMinimum` from its render, the `@loading` shows only once the modules have loaded for `loadingAfter` (and the placeholder its minimum), then stays `loadingMinimum`, the next part waiting (`at`, with `performance.now()`). `visible`, `interaction` and `hover` without a target watch the elements the contexts of the `@placeholder` track in the node of the block, `toIdle` without any. In the tests (`registerDeferBlock` of `utils/defer-testing`, on once `@xaendar/core/testing` is imported) each block registers a `DeferBlockFixture` by its root node, and with `manual` arms nothing. The `interaction` of `armTriggers` (used only by `@defer`: `@hydrate` and a component with a trigger fire it through the events they record) listens in the bubbling phase, so that the listeners of the `@placeholder` handle the event before it is removed; an event the contract recorded on it is replayed at the end of the hydration and fires it.
- An element holding `data-xd-client` (`ssr: { render: false }`) has no declarative shadow root and no server render, and its class may be missing on the server: `_ssrClientComponent` writes it from the metadata the compiler has. `_hydrating` is true, so it waits for its parent like an element to adopt (inputs set first), but `_hasServerRoot` is false, so its first render uses `CREATE_NODES`. In a static template it holds `data-xd-inputs` and starts by itself.
- A static component has no class in the browser: its element stays the HTML of the server, an interactive parent adopts it like any element (`[HYDRATE]` is not there), and its input setters assign plain properties. An interactive component it renders holds `data-xd-inputs` and hydrates as the root of a page.
- The inputs of a component and of a directive are set by property name, never by alias (`_setInput`, `_setExpressionInput`, `_setReactiveInput`, `_resetProperty`): on an element whose class is not defined yet the property is assigned, and `@Property` (or the exposure of a host directive) reads it at the upgrade. `_setProperty` and its variants only write attributes, `String(value)`, removing the attribute for `null` and `undefined` (`updateProperty`): an input found there throws, since the compiler did not recognize it.

The templates compiled for the server (`ssr-compiler`, run by `ssr`) keep the same scopes, one `_Context` per function, but write strings instead of nodes: each function takes `out`, the output buffer (`Array<string | Promise<ServerOutput>>`, the promises standing for the asynchronous structural directives), reads every signal once, and binds no listener. A construct the client renders must render the same HTML on the server: change both generators together.
