# Template runtime model

Compiled templates don't produce a virtual tree: they produce imperative JS that mounts real DOM nodes through the scopes of `core` (`_scope`, `mountNode`, `createAnchor` of `packages/core/src/utils/context/context.util.ts`).

- Each scope (`_Context`) is one lexical scope (root component, or a nested scope from `@for`/`@if`), a plain array of the exact length its layout gives, as Angular's `LView`: `_scope(parent, layout, nodeStrategy?, component?)`, `layout` a constant of the module the compiler writes per block (`_ScopeLayout`: `{ size, nodes, containers?, variables? }`, `const _layout0 = …`), shared by every instance. The header holds the slots every scope has, at the indices of `costants.ts` (`PARENT` the declaring scope, `PARENT_NODE` the node its top nodes are inserted into, `STATE` the pass of its last refresh, `COMPONENT`, `STRATEGY` `null` for `CREATE_NODES`, `CLEANUP` the cleanups and bindings as one item or an array from the second, `LAYOUT`), `HEADER` slots in all (the compiler's `SCOPE_HEADER`: change both together); then the variables (`@let`, the variables of a `@for`, the parameters of a template, the element refs, the error of a `@catch`), each at a slot the compiler assigns, then the nodes at the top of the block, from `layout.nodes` to `layout.containers` (`nodesEnd`), then the containers of its blocks, to the end. Each block (`@if`, `@switch`, `@for`, `@defer`, `@try`, `@hydrate`, `@client`, `@render`, an element with structural directives) holds what it shows in its container: the scope shown or `null`, the `ForRun` for a `@for` (its `rows` and `keys`, arrays of the exact number of items, rebuilt by each run, the rows to reuse found through a `Map` dropped at the end of the run). The constant of the block carries the index of its container among the ones of its scope (`container`, left out for the first: `containerSlot(scope, container)` adds `layout.containers`), since the compiler counts the blocks after the nodes. There is no list of children: `clear`, `refresh` and `setNodeStrategy` walk the containers (`forEachChild(scope, visit, argument)`, `visit` a function of a module), so removing rows is linear. The scopes the runtime creates outside of the containers are held by a cleanup of the scope (`ScopeHolder`, `{ scope }`), which clears, refreshes and gives its strategy to the scope it holds: the branch of a conditional binding (its `ConditionalBindingRun`, registered after the binding selecting the branch) and the scope of a component `createComponent` creates (`moveTo` moves only cleanups). Every function of `utils/context` takes the scope as its first argument: there are no methods and no lookup by name. The generated code reads a variable with `_read(context, depth, slot)`, `depth` being how many `PARENT`s up its declaring scope is, writes one with `_set(context, depth, slot, value)`, and declares an element ref or a `@let` before its value with `_declare(context, slot, kind?)`: the slot holds one of the two `UNINITIALIZED` symbols, and `_read` throws a `ReferenceError` naming it from `layout.variables`. The root of a render has `null` as parent, like the staging scopes the runtime creates (`EMPTY_LAYOUT`, `ELEMENT_LAYOUT` for the scope of the element of `createComponent`, `STRUCTURAL_LAYOUT` for an element with structural directives: the element, then the container of the scope of its content). An event handler is a function of the module of the template, bound by a `TemplateListener` with the context it is declared in: it reads the variables through the context when the event fires, so it sees their current values.
- The bindings of a template (texts, attributes and classes, conditional bindings, the conditions of `@if` and `@switch`, the items of `@for`, the arguments of `@render`, the values of `@let` and the default values of the parameters, `when` of `@defer` and `@hydrate`) go through `_bindEffect(context, callback, first, second?, third?, reads?)` (`signals/effect`): a callback declared once at module level and its arguments, never a closure, the expression of the template being one of the arguments: a function of the module of the template, kept with the context and called `expression.call(context[COMPONENT], context)`. What the generated code passes (the configuration of an element, of a block, of a `@for`, a template) is a constant of its module (`RenderElement`, `BlockConfig`, `ForConfig`, `RenderTemplateConfig`, `_Template`), shared by every instance and never written: the state stays in the run objects. Listeners are `TemplateListener` objects (`handleEvent`, `dispose`), the unbinding of a branch one `AttributeUnbinding`, the branches of a conditional binding applied by a function of the module receiving their target (`ElementBinding`, a directive, the collector of the structural directives). A template (`_Template`, `{ render, parameters }`) takes no slot of its scope: the constant of the `@render` (`RenderTemplateConfig`) carries `depth`, how many scopes up the one declaring the template is, which becomes the `PARENT` of the instance. Its first run, synchronous, happens in the `Computed` of an `EffectNode` (`_runBinding`): when it reads at least one signal the node becomes the effect of the binding, watched by a `Watcher` of its own and read again at once (a source it read may have changed during the run, as the input of a component it rendered: left stale, it would never be notified again), otherwise it is dropped. The variables of the template (the item and the implicit variables of a `@for`, a `@let`, the parameters of a template) are plain values in the slots of the scope, never signals: the compiler gives each variable an identifier unique in its template, a binding reading some of them gets `reads`, a constant array of their identifiers (`const _reads0 = [0];`), and is kept in the `CLEANUP` slot of its scope as a `Binding` (`addCleanup`), whatever it read. A scope whose variables change writes them with `update(scope, slot, value)` (`true` only when the value differs, by `Object.is`) and calls `refresh(scope, ids)`: every binding of the scope and of its descendants reading one of the identifiers runs again (`rerunBinding`), deciding again whether it is an effect (a binding no longer reading a signal drops its effect, one starting to read one gets it), its error reported in a microtask. A refresh started during another one adds its identifiers to the outer ones, and the pass mark (`STATE`) keeps a scope from being refreshed twice in a pass. `_for` refreshes the scope of a reused item with the variables that changed before moving its nodes (its top nodes and the ones of the scopes of its containers, `findItemBounds`), `_renderTemplate` an instance with the parameters that changed (`_Template.parameters`), and `_let` its scope with the identifier of the `@let` (`propagate`, joining the refresh in progress, if any). A signal change runs only the effects reading it, never a refresh.
- An element does not open a context: `renderElementChildren` renders its children in the context of the element, so their effects and listeners are cleared with it, and creates a child context only when their strategy differs (`nodeStrategy.children`, an element created in a hydration) or when the generated function creates one (see `compiler.md`). A scope tracks only the nodes at the top of its block, all rendered into the same node, each in the slot the compiler gave it (the `slot` of its constant, `trackNode(node, parentNode, scope, slot)`): a node rendered into an element has no slot, since it is removed with the element. `_for` moving an item, `_defer` and `createComponent` read the slots of the nodes: never give a slot to a node rendered into an element of the template. The scope keeps the node they are inserted into once (`PARENT_NODE`; the nodes of the server a `@hydrate` keeps until it hydrates, whose number the compiler does not know, go in a scope of their exact count held by the container of the block until the content takes it; `trackNode` throws in development for another one, `DEV_MODE` of `utils/dev-mode`), and its cleanups as the item itself while there is one, an array from the second. The root of a render keeps no node.
- `createAnchor` places a `Comment` node as a stable insertion point for structural directives: dynamic content is always inserted via `insertBefore(node, anchor)`, independently of sibling constructs. The last block of its parent has none (`BlockPosition`, `last: true` in the constant of the block, `true` as the last argument of `_client`): `nodeStrategy.block(…, last)` returns `anchor: null` (`CREATE_NODES` a shared frozen block), and what it renders is appended to the parent, nothing following it there; `ClaimNodes` adopts it from its opening marker alone, the server writing no closing one, its content reaching the end of the parent. Only the compiler decides it (see `compiler.md`): never inside the body of a `@for`, whose items move, nor in the content of a template.
- `clear(scope, detach = true)` destroys a scope: removes its nodes (when `detach`), runs its cleanups, disposes its bindings and clears the scopes they hold (a `ScopeHolder` always removes its nodes: the element of `createComponent` is anywhere), then clears the scopes of its containers. Only the highest scope cleared removes its nodes: a scope of a container removes its own only when they are beside them, in the same node, or when it tracks none; the nodes inside a removed element go with it (`clearChild`). `CustomElement` clears its root with `clear(false)`: a component removed from the DOM is destroyed, its shadow root with it; inserted again (moved by code outside Xaendar), it empties its shadow root before rendering, and a component of the old content connected meanwhile stays destroyed (`_state`).
- A context holds no factory of the elements: `nodeStrategy.element(context, parentNode, tagName, namespace)` creates an element in the namespace its constant names (`RenderElement.namespace`, `createNamespacedElement` of `utils/create-element`: `_createElement` for HTML, `_createSVGElement`, `_createMATHMLElement`).
- The helpers never create nodes directly: they ask `getNodeStrategy(context)`, a `NodeStrategy` (`CREATE_NODES`, or `ClaimNodes` adopting the HTML of the server during the first render of a component rendered on the server). No helper branches on hydration: the strategy is chosen once per component (`CustomElement`) and once per block (`adopt`/`adoptItems` at the first run of `_if`, `_for`, structural elements). `ClaimNodes.end` gives `CREATE_NODES` to the whole tree of contexts (`setNodeStrategy`), so every later run reads `getNodeStrategy(context)` and no helper names the constant. Effects write the DOM only when the value differs (`updateAttribute`, the text compare), so an adopted node is not written again.
- `_hydrate` (`@hydrate`): with the HTML of the server, `skip` passes over its content, owned by the context and inert (events recorded, its code not running) until a trigger fires, then a `ClaimNodes(host, true)` started at its first node adopts it and the events are replayed; `visible`, `interaction` and `hover` become `idle` without elements to watch, which only a block rendering nothing in the end reaches: content sure to render no element is a compile error (`checkTriggerTargets`). The triggers after `prefetch` load the modules once (`loaded` memoized, a failed prefetch silent), `prefetch interaction` firing through the events recorded, like `interaction`; `hover` listens in the capture phase, armed before the recording stops the events (in `deferElementHydration` too). Without the HTML of the server the triggers do not count: the content renders with `CREATE_NODES` once its modules are loaded. An element adopted declaring `data-xd-hydrate` waits for that trigger (`deferElementHydration`), unless it is in the content of a `@hydrate`. `never` returns before the triggers are armed and the events recorded, which would stop them for good: a `@hydrate (never)` keeps its nodes owned by the context and never loads its modules, and an element declaring it never hydrates, unless a `@hydrate` holding it does: the template always wins over the decorator (`ClaimNodes.mount`). A hydration that waited for a trigger is quiet: what differs from the HTML of the server is rendered again without warnings, in the components it adopts too.
- The event contract: `renderToString` writes `eventContract` (`packages/ssr/src/utils/event-contract`) as an inline script after the root of the page. It needs no runtime, records on the document and on every shadow root (`change` and `submit` are not `composed`), and leaves on `window` the queue, under the symbol `_EVENT_CONTRACT_KEY` (`Symbol.for('xaendar.eventContract')`, which the script gets again from its description: `packages/core/src/window.d.ts` declares it on `Window`, so no cast is needed to read it: the projects compiling the sources of core include it next to `globals.d.ts`). The first use of the queue stops it (`takeContractEvents`), or a listener left there would record again what the components handle, replaying it twice. `recordEvents` takes the events on its targets, and a caller with `interaction` fires for them in a microtask; the end of a hydration schedules `replayContractEvents`, a microtask, so that the listeners of a whole tree hydrated in one tick are bound. What goes through an element still waiting stays (`WAITS_FOR_HYDRATION`). Nothing of the triggers reaches the HTML: nothing can hydrate before the runtime. `data-xd-submit` is the only mark, for the one decision that cannot wait: preventing a submission.
- `_client` (`@client`): `replace` removes the `@placeholder` the server rendered, moving the position past its anchor, and the content is created with `CREATE_NODES`, in the same pass of the hydration, without warnings; `CREATE_NODES.replace` does nothing, so no helper branches on it. Inside a `@hydrate` or a component with a trigger it runs when they hydrate. A component of the placeholder is removed without ever hydrating: `disconnectedCallback` then runs no hook, disposing only what its constructor created.
- `_try` (`@try`): renders the content in a holder context, inside a scope (`openTryScope`, `utils/try-scope`) collecting every context created until the content returns, the ones of the components it renders included, since a block registers its context in its parent only once rendered: when the first render throws, they are cleared in creation order (a component is removed, running `onDestroy`, before its own contexts are disposed), and the `@catch` renders with the error, outside the scope. Only the first render is caught, the code of the components the template creates included, as JavaScript catches the functions a `try` calls: inside a scope, `_createElement` constructs a defined custom element with `new` (`document.createElement` reports the error of the constructor instead of throwing it), and `renderElement` mounts through `connectChild`, which throws the error the component handed it from its `connectedCallback` (`runConnection`; the browser reports what a connection callback throws). A component inserted by other code (`appendChild` in `onInit`) runs outside the scope, as the browser reports its error. In a hydration, the classes are defined, and the adopted elements constructed, before the template runs: a constructor throwing there is not caught. `trackNode` removes only a node inserted, as the element whose bindings threw. With the HTML of the server (`<!--xd-t:0-->` content, `<!--xd-t:1-->` catch): the content is adopted, and when it throws the rest is emptied with a warning (`adopt(…, '1')`); a `@catch` of the server is removed silently (`replace`, whose position is past the anchor, so no `close` after it), since its error does not reach the browser, and the block renders from scratch.
- `_defer` (`@defer`): renders its `@placeholder` (with `adopt(…, '')`, so it adopts the one the server rendered between `<!--xd-d-->` and `<!--/xd-d-->`, its listeners bound, then `close`), arms the triggers and the ones after `prefetch` with `armTriggers` of `utils/hydration-triggers` in a microtask, once the template holding the block is rendered (an element ref a trigger names is read then, `target()`), and `when` and `prefetchWhen` with effects, and replaces the part shown with `CREATE_NODES` (a trigger always fires after the hydration): the `@loading` while `load()` runs, then the content, or the `@error` with the error, or, without one, the `@placeholder` again, the error logged. `load` is memoized: the prefetch starts it, silent when it fails, and the trigger rendering the content waits for it. The times: the `@placeholder` stays at least `placeholderMinimum` from its render, the `@loading` shows only once the modules have loaded for `loadingAfter` (and the placeholder its minimum), then stays `loadingMinimum`, the next part waiting (`at`, with `performance.now()`). `visible`, `interaction` and `hover` without a target watch the elements the contexts of the `@placeholder` track in the node of the block, `toIdle` without any. In the tests (`registerDeferBlock` of `utils/defer-testing`, on once `@xaendar/core/testing` is imported) each block registers a `DeferBlockFixture` by its root node, and with `manual` arms nothing. The `interaction` of `armTriggers` (used only by `@defer`: `@hydrate` and a component with a trigger fire it through the events they record) listens in the bubbling phase, so that the listeners of the `@placeholder` handle the event before it is removed; an event the contract recorded on it is replayed at the end of the hydration and fires it.
- An element holding `data-xd-client` (`ssr: { render: false }`) has no declarative shadow root and no server render, and its class may be missing on the server: `_ssrClientComponent` writes it from the metadata the compiler has. `_hydrating` is true, so it waits for its parent like an element to adopt (inputs set first), but `_hasServerRoot` is false, so its first render uses `CREATE_NODES`. In a static template it holds `data-xd-inputs` and starts by itself.
- A static component has no class in the browser: its element stays the HTML of the server, an interactive parent adopts it like any element (`[HYDRATE]` is not there), and its input setters assign plain properties. An interactive component it renders holds `data-xd-inputs` and hydrates as the root of a page.
- The inputs of a component and of a directive are set by property name, never by alias (`_setInput`, `_setExpressionInput`, `_setReactiveInput`, `_resetProperty`): on an element whose class is not defined yet the property is assigned, and `@Property` (or the exposure of a host directive) reads it at the upgrade. `_setProperty` and its variants only write attributes, as `@HostProperty` and the server do (`_attributeValue` of `utils/write-attribute`: `null`/`undefined` remove it, a boolean adds it empty or removes it, but is written as `"true"`/`"false"` on `aria-*` and enumerated attributes, anything else `String(value)`): an input found there throws, since the compiler did not recognize it.

The templates compiled for the server (`ssr-compiler`, run by `ssr`) keep the same scopes with the same layouts, one `_scope` per function, created by the same functions of core, but write strings instead of nodes: each function takes `out`, the output buffer (`Array<string | Promise<ServerOutput>>`, the promises standing for the asynchronous structural directives), reads every signal once, and binds no listener. A construct the client renders must render the same HTML on the server: change both generators together.
