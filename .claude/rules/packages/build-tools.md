# @xaendar/build-tools

Build-time plugins/registry (wiring the compiler into a bundler) plus shared build models/constants. Depends on `common`, `compiler`, `language-core`, `ssr-compiler`.

The hooks never test which environment they run for: they read its strategy, `state.strategies[this.environment.config.consumer]` (`costants/plugin-strategies.ts`, chosen once in `xaendarPlugin`), and call its functions. With the `ssr` option, the server consumer gets `SERVER_STRATEGY`: templates compiled by `compileServer` and registered with `_defineServerRender` of `@xaendar/ssr`, the stylesheet as a string, no type check; the client keeps `CLIENT_STRATEGY`, as does the server without `ssr`. The `config` hook sets `appType: 'custom'`, `configure-server` adds the middleware rendering each page with the entry in place of `<!--xd-ssr-->` (`render(toSameOriginPath(url))`), and `hotUpdate` reloads the page when a module only the server loads changes. `transform` fails on a `styleUrl` leading to a missing file, as a `.css` that cannot be read would otherwise give no stylesheet in silence; `hotUpdate` compiles the component again when that file, or its template, is created. The template module imports, for their side effects, the modules of `resolveTemplateModules`: the files declaring the components and directives it imports (`modulePath`, also through a barrel, which `getImportOrExtract` follows with `resolveExportedClass`) and the modules of the other symbols of the project, not the ones of `@import lazy`; `load` watches them all. `generateTemplateModule` leaves out the static imports of the modules the compiled code imports dynamically (the ones of `@hydrate` and `@defer`), so they become chunks of their own. `SERVER_STRATEGY.filterDependencies` (`getServerDependencies`) leaves out the modules only the content of a `@client`, or the parts of a `@defer` but its `@placeholder`, need. The load hook reports `getTemplateWarnings` of `language-core` through `context.warn`, the same warnings of the editor, once per template: from the strategy with `server`. `transform` gives `compile` the `ssr` option: without the rendering on the server, `@hydrate` and `@client` fail the type-check.

`buildStart`, only in a build with `ssr.staticComponents` (`false` by default, the CLI reads it from the `ssr` of `xaendar.json`; without it a `staticReport` only says there is nothing to report), runs `findStaticComponents` (`utils/static-components`): it reads every component of the project (`findComponentLogic`, `findModuleLogic`, `getTemplateUsage`), the imports of the code (`utils/code-imports`), and spreads what makes a component interactive through the templates until nothing changes (a component the browser may create, `created`: rendered in a block the browser renders again or declared by a module the code imports; it makes interactive everything its template renders, at any depth); the types of the inputs a static component passes are read by `utils/serializable-input`. `transform` compiles the module of static components for the browser with `generateStaticModule`, once checked, and `load` gives the server the `islands` of the template. Nothing of this runs in the dev server: a save can change other components, and they would lose the HMR. The analysis ignores the specs and the entry of the server, which import the root by value.
