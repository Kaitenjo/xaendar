# @xaendar/build-tools

Build-time plugins/registry (wiring the compiler into a bundler) plus shared build models/constants. Depends on `common`, `compiler`, `language-core`, `ssr-compiler`.

The hooks never test which environment they run for: they read its strategy, `state.strategies[this.environment.config.consumer]` (`costants/plugin-strategies.ts`, chosen once in `xaendarPlugin`), and call its functions. With the `ssr` option, the server consumer gets `SERVER_STRATEGY`: templates compiled by `compileServer` and registered with `_defineServerRender` of `@xaendar/ssr`, the stylesheet as a string, no type check; the client keeps `CLIENT_STRATEGY`, as does the server without `ssr`. The `config` hook sets `appType: 'custom'`, `configure-server` adds the middleware rendering each page with the entry in place of `<!--xd-ssr-->` (`render(toSameOriginPath(url))`), and `hotUpdate` reloads the page when a module only the server loads changes. `transform` fails on a `styleUrl` leading to a missing file, as a `.css` that cannot be read would otherwise give no stylesheet in silence; `hotUpdate` compiles the component again when that file, or its template, is created. The template module imports, for their side effects, the modules of `resolveTemplateModules`: the files declaring the components and directives it imports (`modulePath`, also through a barrel, which `getImportOrExtract` follows with `resolveExportedClass`) and the modules of the other symbols of the project, not the ones of `@import lazy`; `load` watches them all. `generateTemplateModule` leaves out the static imports of the modules the compiled code imports dynamically (the ones of `@hydrate` and `@defer`), so they become chunks of their own. `SERVER_STRATEGY.filterDependencies` (`getServerDependencies`) leaves out the modules only the content of a `@client`, or the parts of a `@defer` but its `@placeholder`, need. The load hook reports `getTemplateWarnings` of `language-core` through `context.warn`, the same warnings of the editor, once per template: from the strategy with `server`. `transform` gives `compile` the `ssr` option: without the rendering on the server, `@hydrate` and `@client` fail the type-check. It gives it `strictEvents` too (the library's, else the one of the plugin, `true` by default), and reports the diagnostics of the event names with `this.warn` (`describeEventCheckDiagnostic`), which do not fail the component.

`buildStart`, only in a build with `ssr.staticComponents` (`false` by default, the CLI reads it from the `ssr` of `xaendar.json`; without it a `staticReport` only says there is nothing to report), runs `findStaticComponents` (`utils/static-components`): it reads every component of the project (`findComponentLogic`, `findModuleLogic`, `getTemplateUsage`), the imports of the code (`utils/code-imports`), and spreads what makes a component interactive through the templates until nothing changes (a component the browser may create, `created`: rendered in a block the browser renders again or declared by a module the code imports; it makes interactive everything its template renders, at any depth); the types of the inputs a static component passes are read by `utils/serializable-input`. `transform` compiles the module of static components for the browser with `generateStaticModule`, once checked, and `load` gives the server the `islands` of the template. Nothing of this runs in the dev server: a save can change other components, and they would lose the HMR. The analysis ignores the specs and the entry of the server, which import the root by value.

The `libraries` option (the `libs` of a workspace, resolved by `utils/workspace-libraries`) lets the project import its libraries from their sources: the `config` hook adds the aliases of Vite leading the name of each one to its entry and `name/<path>` beside it (`getLibraryAliases`), `transform` and `load` compile the files under the `root` of a library with its `ssr` and `customElements` (`findWorkspaceLibrary`), and `load` marks the components of a library without `ssr` as rendering only in the browser (`markClientOnly`), so that the server of the project renders them as an application does with the build of the library.

`buildLibrary` (`library/`, the only export besides the plugin) builds a library into a package: `analyzeLibrary` reads its program (`createLibraryProgram`, the `tsconfig.json` of its folder, `rootDir` the folder of the entry), the entries (the entry and every module declaring a component or a directive, by path relative to that folder), the exports of the entry and the selectors, failing on a component outside of the folder or a selector declared twice; `createLibraryManifest` fails on a type of a binding reading a name its module does not export, or a source file outside of the library, before anything is written; a module the type reaches through an alias of the `paths` of `tsconfig.json`, or by the name of the library, is resolved first (`resolveTypeModule`) and written relative to the package, while a package and the declarations of a library of the workspace keep their names. Vite builds it with `createLibraryBuildConfig` (lib mode, ES, not minified, `cssMinify`, `@xaendar/*` and the dependencies external, `attachDebugInfo: 'none'`, the modules of the components marked with side effects), once more into `server/` with the `ssr` of the library; the plugin gets the `library` option, which compiles its files with its options and the `tsconfig.json` of its folder, and with `ssr` gives the server environment `SERVER_STRATEGY` without an entry. `emitLibraryDeclarations` emits the declarations, rewriting the paths leading into the library as relative paths with `.js`, and writes every declaration file of the library (written by hand), which TypeScript does not emit, since the declarations and the types of the manifest may read them. `createLibraryPackageJson` writes the `package.json` (`exports` with `types`, `xaendar-server` with `ssr`, `default`; `sideEffects`; `@xaendar/core` and, with `ssr`, an optional `@xaendar/ssr` as peers, `^` the version compiling it).

A component or a directive of a compiled library comes from `readLibraryMetadata` (`getImportOrExtract`), registered once like the ones of the project (`registerLibraryMetadata`), so that the generator finds it by its selector; `resolveTemplateModules` imports it by `importPath` without watching it. The `config` hook finds the compiled libraries the project depends on (`state.packageLibraries`, from the directory Vite is launched from) and adds `resolve.dedupe` and `optimizeDeps` (`getPackageLibrariesConfig`: their modules included, the packages of Xaendar excluded); `buildStart` registers every selector of their manifests (`registerLibrarySelectors`), which `claimSelectors` rejects for a component of the project, and two libraries defining the same one fail. An owner in a declaration file always keeps its selector. `buildLibrary` clears the registry and the language service first, as every library builds in the same process, and with `dependencies` (the libraries of the workspace it depends on, by the folders of their builds) `withLibraryDependencies` leads their names to the builds in the options of TypeScript of the program and of the plugin, so they are read from their manifests and stay external.
