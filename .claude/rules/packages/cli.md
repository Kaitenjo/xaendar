# @xaendar/cli

The `xd` CLI (via `commander`): `new`, `generate component`, `generate library`, `add library`, `start`, `build`, `test` (Vitest in happy-dom) and `prerender` under `src/commands/`; `start`, `build` and `test` add the plugins of `src/utils/plugins.ts` (Babel decorators, then `xaendarPlugin` with the `customElements` and the `ssr` of `xaendar.json`, read by `utils/xaendar-config`). Depends on `build-tools`, `common`.

When `xaendar.json` declares `ssr` (`entry`, `prerender`, `outDir`, relative to the project, and `staticComponents`, passed to the plugin as `false` unless it is `true`; `entry` without extension, rejected by `resolveSsrPaths` otherwise): `build` runs the build of the server (`build.ssr`, into `dist/server` by default) after the one of the browser, and `prerender` runs `build`, then writes each route rendered by the built entry into the client build. `new --ssr` adds `src/entry-server.ts` and `server.ts` at the root (with `@xaendar/common` among the dependencies; `tsconfig.json` includes it, with the types of Node, and sets no `rootDir`; it imports the built entry by URL, so the project type-checks before its first build), the `ssr` block, `<!--xd-ssr-->` in `index.html` and a client build into `dist/client`. `render(url)` always gets `toSameOriginPath` of the request or of the route (path and query, a single leading slash), in `server.ts`, in the dev server and in `prerender`. The templates never receive the flag: `new` picks `CLIENT_RENDERING` or `SERVER_RENDERING` (`commands/new/rendering`) and the templates read what they need from it.

A workspace is a project whose `xaendar.json` declares `libs`, keyed by the name of the package of each library (`"@acme/ui": { "root": "libraries/ui", "entry", "outDir", "ssr", "customElements" }`): `generate library` creates it in a new folder (`buildStructure` with `library`: the `libs` entry, the `paths` of `tsconfig.json` leading the name to `libraries/<folder>/src`, and a root template rendering the example component of the library), refusing a folder inside a workspace; `add library` adds a library to the project holding the working directory (`readProject` walks up to the nearest `xaendar.json`), writing nothing when `tsconfig.json` is not plain JSON. The files of a library come from `buildLibraryStructure`, the edits of the two JSON files from `utils/library` (`addLibraryToConfig`, `addLibraryPaths`), which `generate component --library` (or run inside a library) also uses to export the component from the entry (`addLibraryExport`). `createPlugins` passes the `libs` to the plugin as `libraries`, and `test` makes Vitest look for the specs in the whole workspace (`dir`), not under the root of Vite only.

`build` in a workspace builds its libraries (`utils/build-libraries`: every one in the order of `libs`, or the one named by its package or its folder, into its `outDir`, `dist/<folder>` by default) with `buildLibrary` of build-tools, passing `createBabelPlugin()` and the version of the CLI; a library depending on another library of the workspace stops it, until the build reads the manifests of the libraries built before. Outside of a workspace, `build <library>` exits with an error.
