# @xaendar/ssr-compiler

Compiles a template into the functions rendering it on the server: `compileServer(input, options)` parses it with `compiler`, resolves its `@import`s when `templateDir` is given, and runs `ServerGenerator`. Depends on `common`, `compiler`, `types` (not on `core` nor `ssr`: the generated code imports them). Used by `build-tools` in the server environments of Vite. Built with tsup (`xaendar.target` node).

- The generator reuses the internals `compiler` exports (`declareScope`, `generator.utils`, symbol imports): every scope (`render`, the branches of `@if`/`@switch`, the body of `@for`, the children of an element with structural directives) is a function called as `key.call(this, out, context, …)`, and the `<template>`s it declares are the functions of the module writing them, taking no slot: `_ssrRenderTemplate(out, context, template_row_12, depth, [args])` climbs `depth` scopes to the one declaring the template. The scopes have the layouts of the client (`_scope(parentContext, _layoutN)`, the variables read with `_read(context, depth, slot)`), and the root one receives the component (`_scope(null, _layout0, undefined, this)`).
- The states under `server-generator/states/` mirror the ones of the client generator. Static text and attributes are escaped at compile time; expressions go through `_escapeText`, `_ssrAttribute` (the whole attribute, left out for `null` and `undefined`, as the client removes it) or `_escapeRawText`; the browser globals are read through `globalThis` (`SERVER_RESOLVE_OPTIONS`), so the ones Node lacks are `undefined` instead of throwing.
- As on the client, what does not change between the elements written is a constant of the module: the element written through the runtime (`div0$element`, `{ tagName, attributes, conditionalBindings, directives }`, passed to `_ssrStartTag`, `_ssrComponent`, `_ssrIsland`, `_ssrClientComponent` with its `div0$client` options), an element of a structural directive (`div0$structural`, whose `render` is the function of the module `div0$render(out, context)`); the expressions of the descriptors and the track of a `@for` are functions of the module receiving the context, called with the component (`declareExpression`). The expressions written inline in the body of a function (texts, plain attributes, conditions) stay inline, read once.
- The `islands` option lists the tags of the interactive components a static template renders, written with `_ssrIsland` instead of `_ssrComponent`.
- `getServerDependencies` picks the modules the module of a template imports: all of them, unless the template holds a `@client` or a `@defer` (whose `@placeholder` alone the server renders) or imports a component declaring `ssr: { render: false }`, then only the ones declaring a component or a directive the server renders, the symbols being imported by the generated code.
- `compileServer` passes the components and the directives the template imports to the generator (`addImportedMetadata`): their inputs are written with the input setters and the name of their property, as the client does, and the ones rendering only in the browser (`isClientComponent`) with `_ssrClientComponent`, whatever the class on the server.
- `generate` writes the events of the template as `render.events`, for the event contract of the page, and an element or a branch with `(submit)` writes `data-xd-submit`, mirroring core's `_SUBMIT_ATTRIBUTE`.
- The values of a `@case` reach the generator as one string (`1, 2`): they become a constant array of the module (`case0_1$values`), tested with `indexOf(__value) !== -1`, strict as the client, allocating nothing.
- A `@try` becomes `_ssrTry(out, context, tryN, catchN)`, the runtime calling them with the component: it writes its markers, as `_ssrStructural` does.
- Element refs are declared as `undefined`: no element exists on the server.
- A `@render` calling an expression writes `_ssrRenderTemplateRef(out, value, [args])`; a template read as a value is `_templateRef(context, depth, template_row_12)` (from core); the `<template name()>` children of a component are written in the `templates` of its constant (`mapContentTemplates`), which `_ssrComponent` passes before the render; a standard `<template>` writes its `content` as is.
- The variables of the template are values, as on the client: the server reads each one once, so a `@let` is written as `_set(context, 0, slot, value)` and the default value of a parameter as an expression (`declareTemplateParameters` with `server`), and `_ssrRenderTemplate` receives the values of the arguments.
- A native element applying custom directives goes through `_ssrStartTag`, its directives (`mapDirectives`: selector and properties, no events) as its last argument and the ones of its branches in their `directives`, so a branch holding only a directive is not empty (`isEmptyBranch(branch, withDirectives)`). The custom directives of a component are left out.
- The last block of nodes ending where their parent does (`ServerParent.end`: the root, the children of an element, the content of a block itself the last one, never the body of a `@for` nor the content of a template) is passed `last` (`isLastRenderedChild` of the compiler, as the client): it writes no closing marker, `toBlockFunction(…, last)` giving its content `end`, `_ssrTry(…, true)` and `last: true` in the constant of `_ssrStructural`, since the client renders it without anchor.
- The generated code writes the markers of hydration as string literals, from `costants/ssr-markers.constants.ts`, which mirrors core's `_SSR_MARKERS` (this package depends on no runtime): `_generateNodes` writes `<!---->` where `getTextSeparators` of the compiler says, which the client generator reads too, the states of `@if`/`@switch`/`@for`/`@hydrate`/`@client`/`@defer` their open and close markers (of a `@client` and of a `@defer` only those and its `@placeholder`, never the other blocks); `@for` compiles its `track` as the client does, for the key of `_ssrItemMarker`.
