# @xaendar/ssr

Runtime of the rendering on the server: `renderToString(component, inputs?, options?)` and the helpers `ssr-compiler` code calls (`_ssr*`, `_escape*`, `_defineServerRender`). Depends on `common`, `types`; `@xaendar/core` and `@xaendar/internals` are exact peerDependencies (one copy of their module state). Built with Vite (`xaendar.target` browser), run by Node.

- `@xaendar/ssr/dom` (`src/dom/index.ts`): `loadServerDom()` installs a minimal `HTMLElement` and `customElements` on `globalThis`, and the native classes (`HTMLButtonElement`…) as that `HTMLElement` (so `customElementOf` gives `CustomElement` on the server), keeping existing ones.
- A customized built-in element is found by `is` (`ServerElementConfig.is`), written as the first attribute; without a template (no server render) `_renderComponent` writes no shadow root but `data-xd-client`, so the browser waits for its hydration; a void root gets no end tag. It runs before core is evaluated, so nothing under `src/dom` imports core.
- Component code runs inside `_runOnServer(runtime, fn)` with the page's runtime (`_createServerRuntime(state)`): `effect()` does nothing, `createComponent()` constructs without rendering, `getTransferState` reads that page's `state`, so concurrent renders share nothing; async parts capture the runtime and run in it again. Never run on the server: effects, `afterRender`, `onDestroy`, listeners, `@HostListener`, host directives, a component's custom directives, queries; element refs are `undefined`.
- `_ssrStartTag` applies a native element's custom directives (own, then selected branches') after its bindings: `_resolveDirective`, `new`, `_SET_DIRECTIVE_ELEMENT`, property setters, `onInit`, `_applyHostAttributes`, each with its `order`; never `DIRECTIVE_CONNECT` (listeners, host effects). Elements written through the runtime create the `class`/`style` states before their bindings and merge every other attribute (`prepareStyling`, `_mergeAttributes`), so precedence matches the client whatever the order. A `ServerElement.innerHTML` set there is written unescaped right after the start tag.
- `_renderComponent`: construct, bind inputs, `onInit`, reserve the start tag, write the declarative shadow root (`<template shadowrootmode="open">` plus `shadowrootdelegatesfocus`, `shadowrootslotassignment="manual"`, `shadowrootserializable`, `shadowrootclonable` read from the `ServerShadowRoot` the element attached with the `shadowRoot` options; no slot is assigned on the server, one `<style>` of the stylesheets (`_defineServerRender` joins the `css` strings, empty ones left out), a slot for the `<style data-xd-style>` of the inline styles, render), apply host attributes and a non-`load` trigger (`data-xd-hydrate`), fill the start tag. `_ssrIsland` (interactive child of a static template) always writes its bound inputs into `data-xd-inputs` by property name. A custom element without class or server render is a plain element. `_ssrClientComponent` (`ssr: { render: false }`) constructs nothing (its class may be missing): attributes yes, inputs only in a static template (`data-xd-inputs`), plus `data-xd-client`; `renderToString` of such a root uses `_writeClientRoot`.
- No `style` attribute is written in a page: `writeStartTag` moves it into a rule of the `ServerStyles` of the current tree (`ServerRuntime.styles`: the shadow root rendering, swapped by `_renderInTree`; the page around the root, written before it by `renderToString`), the element holding `data-xd-style="<index>"`; equal blocks share a rule. `addStyleRule` keeps only declarations whose name is a property and whose value cannot end the rule (`staysInDeclaration`: no `{`/`}`, `;` outside brackets, comment, open string or bracket, trailing escape), since a user value could restyle the page. The selector `:is([data-xd-style="N"],#a#b#c#d#e)` has the specificity of five IDs, standing for the attribute (never `!important`). The slot is filled after the render (`writeShadowStyles`): a string, or a promise settling once the async parts are rendered (`_ssrStructural` renders them with the styles it captured). Outside a page (helpers called by themselves) no runtime has `styles`: the `style` attribute stays. `options.nonce` (`ServerRuntime.nonce`, `writeNonceAttribute`) goes on every `<style>` and on the event contract.
- `renderToString` writes the root's `data-xd-inputs` and `options.state` (`<script type="application/json" data-xd-state>`) with core's `_stringifyState` before running component code, then the event contract (`utils/event-contract`) right after the root, before the state, with the events collected in `ServerRuntime.events` (`render.events` and `@HostListener`); `options.nonce` goes on the script and on every `<style>`. `eventContract` is written as its own text: it reads nothing outside its parameters.
- `_ssrTry` renders a `@try` into its own output, kept with `<!--xd-t:0-->` or replaced by the `@catch` with `<!--xd-t:1-->` when it throws, components' code included.
- Serialization follows `@xaendar/internals`: texts escape `& < >` (`null`/`undefined` empty), attributes `& " < >` (`null`/`undefined` not written, like core's setters), raw text elements only neutralize their end tag, void elements get none, a `\n` follows the start tag of `pre`, `textarea`, `listing`. Dynamic parts are marked with core's `_SSR_MARKERS`.
- End-to-end specs compile real templates: `render-to-string.spec.ts` (`compileServer`) and `hydration/hydration.spec.ts` (both generators, happy-dom). A new template construct needs a case in both.
