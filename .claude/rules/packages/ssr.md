# @xaendar/ssr

Runtime of the rendering on the server: `renderToString(component, inputs?, options?)` and the helpers `ssr-compiler` code calls (`_ssr*`, `_escape*`, `_defineServerRender`). Depends on `common`, `types`; `@xaendar/core` is an exact peerDependency (one copy of its module state). Built with Vite (`xaendar.target` browser), run by Node.

- `@xaendar/ssr/dom` (`src/dom/index.ts`): `loadServerDom()` installs a minimal `HTMLElement` and `customElements` on `globalThis`, keeping existing ones. It runs before core is evaluated, so nothing under `src/dom` imports core.
- Component code runs inside `_runOnServer(runtime, fn)` with the page's runtime (`_createServerRuntime(state)`): `effect()` does nothing, `createComponent()` constructs without rendering, `getTransferState` reads that page's `state`, so concurrent renders share nothing; async parts capture the runtime and run in it again. Never run on the server: effects, `afterRender`, `onDestroy`, listeners, `@HostListener`, host directives, a component's custom directives, queries; element refs are `undefined`.
- `_ssrStartTag` applies a native element's custom directives (own, then selected branches') after its bindings: `_resolveDirective`, `new`, `_SET_DIRECTIVE_ELEMENT`, property setters, `onInit`, `_applyHostAttributes`, each with its `order`; never `DIRECTIVE_CONNECT` (listeners, host effects). Elements written through the runtime create the `class`/`style` states before their bindings and merge every other attribute (`prepareStyling`, `_mergeAttributes`), so precedence matches the client whatever the order. A `ServerElement.innerHTML` set there is written unescaped right after the start tag.
- `_renderComponent`: construct, bind inputs, `onInit`, reserve the start tag, write the declarative shadow root (`<template shadowrootmode="open">`, `<style>`, render), apply host attributes and a non-`load` trigger (`data-xd-hydrate`), fill the start tag. `_ssrIsland` (interactive child of a static template) always writes its bound inputs into `data-xd-inputs` by property name. A custom element without class or server render is a plain element. `_ssrClientComponent` (`ssr: { render: false }`) constructs nothing (its class may be missing): attributes yes, inputs only in a static template (`data-xd-inputs`), plus `data-xd-client`; `renderToString` of such a root uses `_writeClientRoot`.
- `renderToString` writes the root's `data-xd-inputs` and `options.state` (`<script type="application/json" data-xd-state>`) with core's `_stringifyState` before running component code, then the event contract (`utils/event-contract`) right after the root, before the state, with the events collected in `ServerRuntime.events` (`render.events` and `@HostListener`); `options.nonce` goes on the script. `eventContract` is written as its own text: it reads nothing outside its parameters.
- `_ssrTry` renders a `@try` into its own output, kept with `<!--xd-t:0-->` or replaced by the `@catch` with `<!--xd-t:1-->` when it throws, components' code included.
- Serialization follows `@xaendar/common`: texts escape `& < >` (`null`/`undefined` empty), attributes `& " < >` (`null`/`undefined` not written, like core's setters), raw text elements only neutralize their end tag, void elements get none, a `\n` follows the start tag of `pre`, `textarea`, `listing`. Dynamic parts are marked with core's `_SSR_MARKERS`.
- End-to-end specs compile real templates: `render-to-string.spec.ts` (`compileServer`) and `hydration/hydration.spec.ts` (both generators, happy-dom). A new template construct needs a case in both.
