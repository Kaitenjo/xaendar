# @xaendar/ssr

The runtime of the rendering on the server: `renderToString(component, inputs?, options?)`, and the helpers the templates compiled by `ssr-compiler` call (`_ssr*`, `_escape*`, `_defineServerRender`). Depends on `common`, `types`; `@xaendar/core` is an exact peerDependency, so the application and the server share one copy of its module state. Built with Vite (`xaendar.target` browser), although it runs in Node.

- `@xaendar/ssr/dom` (`src/dom/index.ts`, a secondary entry point): `loadServerDom()` installs a minimal `HTMLElement` and `customElements` on `globalThis`, keeping the ones already there. It runs before `@xaendar/core` is evaluated, so nothing under `src/dom` imports core.
- Component code runs inside `_runOnServer(runtime, fn)`, which swaps core's `_ComponentRuntime` for the one of the page (`_createServerRuntime(state)`): `effect()` does nothing, `createComponent()` constructs without rendering and `getTransferState` reads the `state` of that page, so concurrent renders never share it. The asynchronous parts capture the runtime and run in it again. Effects, `afterRender`, `onDestroy`, listeners, `@HostEvent`, host directives, the custom directives of a component and queries never run on the server; element refs are `undefined`.
- `_ssrStartTag` applies the custom directives of a native element (its own, then the ones of the selected branches, `ServerDirective`/`ServerBindings.directives`) once its bindings are: `_resolveDirective`, `new Directive()`, `_SET_DIRECTIVE_ELEMENT` to the `ServerElement`, the setters of the properties, `onInit`, `_applyHostProperties`; never `DIRECTIVE_CONNECT`, which binds listeners and host effects. A `ServerElement.innerHTML` assigned there is written right after the start tag, unescaped, before the children of the template: an element filled by a directive has none.
- `_renderComponent` constructs the element, binds its inputs, runs `onInit`, reserves the slot of its start tag, writes the declarative shadow root (`<template shadowrootmode="open">`, the `<style>`, the render), applies the host properties and the trigger of `@WebComponent({ ssr: { hydrate } })` other than `load` (`data-xd-hydrate`), then fills the start tag. `_ssrIsland`, for an interactive component a static template renders, writes the inputs bound there into `data-xd-inputs`, by the name of their property, always, since the attribute tells the browser to hydrate it by itself. A custom element without class or server render is written as a plain element. `_ssrClientComponent` writes a component declaring `ssr: { render: false }` from what the compiler knows of it, constructing nothing, since its class may be missing: attributes yes, inputs (the bindings with the input setters) no, unless the template is static (`data-xd-inputs`, their expressions read only then), with `data-xd-client`. `renderToString` of such a root (`_isClientComponent`, `_writeClientRoot`) writes the same element from the metadata of the class.
- `renderToString` writes the event contract (`utils/event-contract`) right after the root, before the transfer state, once the page is rendered: `_renderComponent` collects in the runtime of the page (`ServerRuntime.events`) the events of `render.events` and of `@HostEvent`. `options.nonce` goes on the script, for a strict `Content-Security-Policy`. `eventContract` is written as its own text, so it reads nothing outside of its parameters, and is covered as a function by its spec.
- `_ssrTry` renders the content of a `@try` into an output of its own, kept with `<!--xd-t:0-->`, or dropped for the `@catch` with `<!--xd-t:1-->` when it throws, the code of the components it renders included (`_renderComponent` runs it in the render of the template).
- Serialization follows `@xaendar/common`: texts escape `& < >` (`null` and `undefined` are an empty text, as `textContent` writes them), attributes `& " < >` (an attribute bound to `null` or `undefined` is not written, `_ssrAttribute` and the setters of core alike, as the browser removes it), raw text elements only neutralize their end tag, void elements get no end tag, and a `\n` always follows the start tag of `pre`, `textarea` and `listing`.
- The output marks the dynamic parts with the comments of core's `_SSR_MARKERS` (`_ssrStructural` and `_ssrItemMarker` write theirs, the generated code the others). `renderToString` writes the inputs into `data-xd-inputs` of the root and `options.state` into a `<script type="application/json" data-xd-state>` after it, both with core's `_stringifyState`, before running any component code.
- The end-to-end specs compile real templates: `render-to-string.spec.ts` with `compileServer`, `hydration/hydration.spec.ts` with both generators (happy-dom, the declarative shadow roots attached by hand, the browser classes defined after the HTML is loaded). A new template construct needs a case in both.
